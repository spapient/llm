# 0016：线协议第 2 版——增量解码、载荷上限与帧级 CRC-32

- 状态：已采纳
- 日期：2026-11-12

## 背景

`proto` 的第一版只落地了"10 字节帧头 + 载荷"：魔数、版本、类型、长度各一个字段，
`Envelope::frame` / `Envelope::parse` 一对编解码。它能证明布局自洽，但按这套接口写不出一条
真实的连接，三个缺口都在"对端不可信"这一侧：

1. **只有整帧接口**。TCP / 管道上读到的是字节流：一帧可能只到了半个帧头，一个读缓冲里也可能
   躺着好几帧。调用方只能自己维护半个缓冲再切片，而"这一帧多长"要重算一遍长度与版本的规则
   ——每多一个调用方就多一份可能与 `parse` 不一致的实现。
2. **载荷长度没有上限**。`len` 是 `u32`，对端写 `0xFFFF_FFFF` 时，接收方要么拒绝，要么替对端
   分配 4 GiB。第一版只在 32 位平台上修掉了算术溢出，没有回答"该不该收下"。
3. **长度对得上不等于内容对得上**。长度字段与类型字段都被校验过，载荷没有任何覆盖：一个比特
   翻转的载荷会被当成合法数据送进模型，只在若干层之后表现成"这轮输出很奇怪"。

这三条都不是"再多写点功能"，而是"这个格式能不能用于真实连接"。

## 决策

### 1. 帧布局：v2 只在末尾加 4 字节，帧头一个字都不动

```text
v1: magic(u16) | version(u16) | kind(u16) | len(u32) | payload[len]
v2: magic(u16) | version(u16) | kind(u16) | len(u32) | payload[len] | crc32(u32)
```

全部小端。`HEADER_LEN = 10` 对两版都成立，`TRAILER_LEN = 4` 只属于 v2。CRC-32（IEEE 802.3）
覆盖**帧头 + 载荷**，不含校验尾自己——否则它无法被独立核对。

把校验尾放在末尾而不是塞进帧头，是因为帧头已经固定：挪一个字节等于让所有 v1 对端失配，而
"末尾多一段"是版本字段本来就允许的演进。`Envelope` 在往返里保留版本（`Envelope::version`），
所以收到的 v1 帧不会被本端"顺手升级"成 v2。

### 2. 版本规则：0 是 bug，过新是升级，两者类别不同

`Version::FIRST = 1`、`Version::CURRENT = 2`、`is_supported` 为 `FIRST..=CURRENT`：

| 收到的版本 | 类别 | 含义 |
|---|---|---|
| `1` / `2` | — | 接受 |
| `0` | `invalid` | 本端或对端的 bug，重试没有意义 |
| `> CURRENT` | `unsupported` | 对端比本端新，升级本端即可 |

编码侧同样自检：本端写不出版本 0，也写不出自己解不出来的版本——一个解不出来的帧不该被写出去。

### 3. `MAX_PAYLOAD = 1 MiB` 是协议常量，不是配置项

接收方的上限必须与发送方一致，否则"本端写得出、对端收不下"会变成一个只在特定连接上出现的
失败。上限定在 1 MiB：一帧是一段字节块（不是一条完整请求），更大的载荷切成多帧本身就更合理，
而 1 MiB 让"每连接最多占用多少"可以心算。

超限的声明**在帧头到达时**就被拒绝：十个字节换一次拒绝服务是这个格式最容易犯的错。

### 4. 一个解码器，三种结局，永不重同步

`Decoder::push` 追加字节、`Decoder::next_frame` 取帧，返回 `Result<Option<Frame>>`：

- `Ok(None)`：还没到齐（半个帧头，或整帧不够）——不是错误，连接上的字节本来就分批到；
- `Ok(Some(frame))`：有一帧，载荷是**借来的**（`Frame`），处理完再取下一帧时零复制；
- `Err`：这条流坏了。

"坏了"是一次性的：帧头坏掉之后没有可靠的重同步点（长度字段本身可能正是坏掉的那部分），
所以第一次失败之后每次调用都返回同一个错误，继续喂字节也不会"运气好又对上"；复用对象解下一条
连接必须显式 `reset`。`finish` 区分"读完"与"读到一半断了"——把后者当成前者是这个协议能犯的
最安静的错。

内存有上界：缓冲不超过"一次 `push` 的量 + 一帧"，已交付的前缀在 `push` 里压缩，且只在
"挪掉的不少于留下的"时才拷一次，摊还仍是每字节 O(1)。

### 5. 编码：复用缓冲，失败不留半帧

`Envelope::encode_into(&mut Vec<u8>)` 先自检（版本可编码、载荷不超限）再写，所以失败时调用方的
缓冲原样不动——流里不会出现一截没有帧头的字节。`frame()` 只是它的分配封装，
`encoded_len()` 用它算容量。

### 6. 边界不变：`proto` 仍然不拥有请求语义

这一版只补"字节 → 帧"，不搬 `Request` / `Event` / `Command` / 采样参数 / 端口 trait。那些类型的
主人是 `serve`、`engine`、`nn`、`kv`（`docs/ARCHITECTURE.md` 第三节），协议层越界会把"帧怎么
分"和"消息说什么"重新搅在一起——第 1 版的边界是对的，只是能力不足。

## 后果

- 一条真实连接现在只需要"读 → `push` → 循环 `next_frame` → 处理 → `finish`"，不必自己维护
  半帧缓冲，也不必重算帧长。
- v1 帧照旧可读，`serve` 的调用点一行未改（`Envelope::new` / `frame` / `parse` / `payload` /
  `kind` 的签名不变）。
- 代价：v2 每帧多一次 CRC（1 MiB 上限下是微秒级），以及 4 字节的线上开销。两者都落在"每帧"
  而不是"每个字节"的量级上。
- 用例把每条判据都钉住：字节布局（含 v1 与 v2 的差异）、版本 0 / 过新、超限声明、载荷翻转、
  逐字节喂入、随机切分、坏帧后不重同步、断连与 `finish`、反复收发的缓冲不增长。

## 未决（后续阶段）

- **套接字后端**：`Decoder` 已经是"协议侧的全部状态"，`Read` / `Write` 的驱动留给 `serve` 的
  P1 服务器（阻塞与异步各一份，协议层不引入运行时）。
- **帧级压缩**：`pack` 的 codec 字段是为权重容器留的；线协议若要压缩，应当作为新的 version
  演进（载荷格式变，帧头不变）。
- **心跳 / 空闲超时**：属于连接管理，不是帧格式；`Kind` 闭集暂不扩（加一个变体要同步
  `Kind::ALL`、`code` 与对端行为）。
