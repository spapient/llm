# 0038：crate 合并节奏（D4）

- 状态：已采纳（D4 决策；本轮不合并，登记触发条件）
- 日期：2026-11-19
- 相关：[0019](0019-packaging-merge.md)（七条吸收链的成员合并）、[0020](0020-settings-layer-absorption.md)（设置层吸收）、[0021](0021-toml-layer-into-diagnostic.md)（TOML 语法层并入 `diagnostic`）、[0023](0023-settings-to-cli.md)（策略上移 `cli`）；看板见 [`../implementation-task-plan.md`](../implementation-task-plan.md) §4 D4，分析取证见 [`../10k-analysis.md`](../10k-analysis.md) §6.2 第 1 条、[`../REPO-review-2026-11.md`](../REPO-review-2026-11.md) §2.7

## 背景

`10k-analysis.md` §6.2 给过一条结构减法路线：把成员从当时的 31 收到约 8 个"模块式"成员。与此同时，本仓的可执行架构门禁（`crates/testkit/tests/architecture.rs`）正建立在**成员边界**之上：层表与表内顺序构成偏序、依赖边逐条声明、"一个类型一个主人"按 `crates/<主人>/src` 双向校验。成员数量因此不是一个纯粹的行数问题，而是架构门能守住多少边界的直接函数。

ADR 0019–0023 已经用"吸收 / 拆分后删除"的方式把成员从 33 收到 **25**（含根包）、依赖边从 106 收到当前 113 条（`REPO-review` 基线）。这些历史合并的共同前提是：**被吸收的成员要么没有单一消费者、要么消费者就在同一个 absorbing crate 里**。它证明可行的合并形态是"单一消费者 + 同层被吸收"，而不是按目录打包。

于是要裁决：是否在本轮继续做模块式合并，以及今后合并的判据。

## 决策

### 1. 维持 25 个 `crates/*` 成员到 M2

本轮不做成员合并。理由不是"合并永远不该做"，而是当前没有满足既有历史前提的候选。

### 2. M2 后只合并"单一消费者 + 同层"的叶子成员

今后任何成员合并必须同时满足三点：

- **叶子**：被合并成员只被一个成员依赖，或只依赖一个成员；
- **单一消费者**：真正需要它的产品代码只有一处，而不是"几乎所有层都顺手 use 一下"；
- **同层**：两个成员落在同一层，或依赖方向合法（合并后不产生反向边）。

"同层"不是形式主义：合并一个低层成员进高层成员，会让高层把低层的依赖面整块吞下，架构门的层序断言随之失效。ADR 0019 的七条吸收链全部满足"同层向左"或"跨层向下"，因此一条方向断言都不需要放宽。

### 3. 合并以实证为据，不按目录猜

合并必须给出边数 / 机制行数 / 编译时间的可复跑对照（同 M1-C1 分账口径），并说明消失的是哪些边。没有数字的"看起来内聚"不构成合并理由。

### 4. 当前剩余单生产消费者叶子全部跨层，无同层候选

复核当前树，仍有若干"单生产消费者"的叶子成员，但它们**全部跨层**，不满足 §2 的同层条件：

| 成员 | 唯一消费者 | 关系 |
|---|---|---|
| `rng` | `serve` | 跨层向下 |
| `tokenizer` | `serve` | 跨层向下 |
| `autograd` | `train` | 跨层向下 |
| `data` | `train` | 跨层向下 |
| `shard` | `train` | 跨层向下 |

把其中任何一个并入消费者都会让高层吃掉一个低层的依赖面，与"依赖只指向更低层"的层序断言冲突。同层内现有成员各自有多个消费者（例如 L1 的 `dtype`/`diagnostic`/`tensor`、L3 的 `op`/`prof`/`prim`），也不满足"单一消费者"。因此本轮**没有**合格的合并候选。

## 备选与否决

**立即 31→8 模块式合并**：否决。理由：

- 会把编译期并行、架构门的方向判定与"一个类型一个主人"的边界检查一起抹掉，这些是本仓当前最强的治理资产（`REPO-review` §0.1）；
- 模块式合并的收益（更少成员、更短编译链）没有实测对照，而代价（边界不可执行化）是确定的；
- 合并若只为压成员数，会把"单一消费者"这一已被证明有效的判据让位给"目录看起来像一家人"。

**按目录猜合并**：否决。目录名称不是依赖关系，按名合并会制造反向边或同层乱序，架构门会当场报红——届时只能放宽断言，等于用破坏门禁换成员数。

## 后果

### 正面

- 成员边界继续作为架构门的可执行单元；"一个类型一个主人"与依赖方向无需放宽；
- 合并判据显式化：将来任何合并必须同时给出"叶子 + 单一消费者 + 同层 + 实证"，不能靠直觉。

### 负面（代价）

- 成员数维持 25，编译单元数不减少；单个 crate 内的机制行数继续偏大（如 `weights`/`cutile` 的单文件），这些靠文件级拆分消化，而不是靠成员合并。

### 重议条件

- M2 落地后出现新的"单一消费者 + 同层"叶子成员；
- 编译时间 / 链接时间 / RSS 的实测对照显示成员边界本身是瓶颈；
- 出现必须以合并才能消除的重复（两份平行实现跨成员漂移，且无法用一个主人收口）。

## 不做

- 不在本轮合并任何 crate，不改任何成员的 `Cargo.toml` 依赖集合；
- 不裁决 `fuzz` / `benches` 的 members 归属——它们是工具成员、架构门豁免，是否移出 members 属另一独立决策；
- 不改变 ADR 0019–0023 已落地的吸收结果。
