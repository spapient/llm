# 0027：内核注册表形状与片段契约边界

- 状态：提议（P0 落档抽象形状；注册表实现与后端内核随 P1 CPU、P3 Metal/CUDA 落地）
- 日期：2026-11-15
- 相关：[0025](0025-runtime-backend-abstraction.md)（后端三件套、算子多后端挂载）、ADR 0026（算子泛型骨架）、ADR 0012（量化权重同源）

## 背景

`prim` 是跨设备源码片段仓库，不是可执行内核层；P0 片段是标量语句块，tile / SIMD / 设备指令落点划归 P1/P3（roadmap §6）。对标 llama.cpp / candle / burn / TRT-LLM（评审 §2），当前原型在抽象层有三个若不在 P0 定死、到 P3 双后端并行就会返工的缺口：

1. **没有内核注册表形状**：`cutile::build` 按 `(vendor, ext)` 从目录取片段（`crates/cutile/src/build.rs:361-371`）；协商只回答"设备有没有这条签名"，缺少"原语 × 后端 × 签名 → 具体内核实现"的挂载点与键。P3 接 Metal + CUDA 时，同一原语要挂多条后端实现，没有注册表形状就会在算子 / 调度里长出厂商特判分支。
2. **片段参数没有类型化契约**：`splice` 只校验槽位有无实参（`crates/cutile/src/substitute.rs:124-140`）；参数的 dtype / 空间 / lane / 对齐维度靠注释约定，装载期不与档案 `provides` 属性交叉核对。
3. **跨设备片段与解析规则靠人保持一致**：`dot` / `quant` 五份正文逐字同构；签名解析规则在 `prim` 与 `build.rs` 各抄一份（评审 C1），规则漂移会让构建期校验与运行期装载不一致。

本 ADR 在不引入后端、不引入 `unsafe`、不引入通用 IR（ADR 0017）的前提下，把通向多后端的抽象形状定死；第一版可以只有编译期类型与校验，不出真实内核。

## 决策

### 1. 注册表键：七元组，能力闭集为选择唯一依据

一条内核实现由键 `(prim, impl, dtype, space, lanes, arch, block)` 标识：

- `prim`：原语闭集（`prof::atom::Prim`）；
- `impl`：实现名，与档案 `provides.impl_name` 同源（如 `scalar_f32` / `fma` / `dp4a` / `mmad` / `wgmma`）；
- `dtype`：元素类型闭集（f32 / i32 / i8 / i4 / u8 …）；
- `space`：存储层级闭集（GM / FAST / REG）；
- `lanes`：子组 / 向量宽度（标量为 1）；
- `arch`：指令集 / 后端标识（`cpu` / `neon` / `avx2` / `metal` / `cuda` …），只作登记标签，不进热路径 `match`；
- `block`：分块宽度（tile 尺寸 / 量化块宽），标量实现记 `1`。

注册表选择只走 `prof` 档案见证过的能力闭集；模型与调度代码里不出现 `if Metal {} else if CUDA {}` 的厂商特判（沿用 ADR 0025 §7）。`arch` / `block` 维度现在入键形状，为 P1 的 plan 层（按形状 / 批次 / 指令集选最优内核）预留位置，本轮不实现选择算法。

### 2. 挂载点：声明与实现分离，实现挂后端侧

- `op` 的 `REGISTRY` 继续只持算子声明、模板与标量参考，不挂设备内核（ADR 0025 §4）。
- 注册表条目 = 键 → 挂载句柄：P0/P1 阶段句柄是 `prim` 片段文本 + 档案见证入口；P3 阶段由独立后端边界 crate 挂载设备内核（不透明句柄藏在 `Allocator` 返回类型后，ADR 0025 §2）。
- 注册表类型契约先定义在 `cutile` 协商侧（与 `cap` / `build` 同层），不新增 crate；后端边界 crate 只依赖这套键与 trait 形状，依赖方向不反向（ADR 0001）。

### 3. 片段契约：装载期交叉核对档案属性

片段绑定的参数维度（dtype / space / lanes / align / axis / op / sat / group / stages …）必须与档案选中的那条 `provides` 属性对齐：

- P0 已有的对齐：片段声明的 `(prim, impl)` 在档案里有对应 `provides` 且带 witness（`build.rs:249-283`）。
- P0 本轮补：解析规则单源化（§5）；参数维度校验的形状在本 ADR 定档，代码校验随 P1 首条真实内核一起落地——`FragmentSet` 装载时需要传入对应 `Profile`，把片段槽位引用的维度与 `provides.attrs` 逐条核对，越界或缺配即 `invalid`（评审 C2/C4）。
- 片段不自己声明类型语义；类型事实源是档案 `provides`，片段文本只实现档案选中的那一条签名。

### 4. 片段复用：标量语义单一事实源，外壳保留设备空间

- 标量算术的事实源是 `op` 的标量参考（`reference`），片段不另立一套数值口径；片段与参考对拍一致由 witness / `cutile::verify` 守。
- 设备语言外壳（C / CUDA / OpenCL / AscendC / MSL）保留在各 vendor 目录，为 P3 手写指令集特化留空间——不现在就把五份文本压成一个模板生成器。
- 本轮先落**同构一致性校验**：生成器核对同原语跨 vendor 的片段正文，除允许差异（impl 名、语言注释、设备指令名）外逐字一致；出现第二套真实算法（如标量 vs dp4a）时才按 impl 分支维护。模板展开延后到算法分化、且手写内核空间被证明受限时再上。

### 5. 签名解析单源化

抽一份零依赖、纯字符串的签名规则到 `crates/prim/src/signature.rs`：剥 `/* */` 外壳、去 `cutile-sign:` 标记、按 `/` 切 `(prim, impl)`。

- `prim` crate 经 `mod` 引入；`build.rs` 经 `include!("src/signature.rs")` 引入同一份文本。构建脚本不能依赖正在构建的 crate 编译产物，但可以 include 同一份纯函数源码——规则因此只有一份，不再双份抄写。
- 共享层不认识原语闭集、不构造诊断错误：闭集比对、impl 非空判定、错误格式化留在各自调用方（crate 用 `diagnostic::Error`，build.rs 用 `fail`）。

### 6. 缓存指纹纳入内核身份

产物缓存（`cutile::cache`）内容寻址键在现有 source / tool / 版本等字段之外，预留内核身份字段：`impl` / `arch` / `block`。P0 先把字段形状定进键结构，P1 填值；同原语不同实现的产物在缓存里必须是两条独立条目，不能互相命中（评审 C5）。

### 7. 量化格式走独立 trait，不塞进片段

块量化格式（Q4_0 / Q8_0 / K-quants / FP8）的打包、解包、点积绑在同一格式 trait 上（对标 ggml / candle 块格式），片段只做该 trait 展开后的解包与乘加；新量化格式不回改权重读取（衔接 ADR 0012、roadmap §5 量化抽象行）。格式 trait 属 P1 解耦、P3 填格式与内核，本 ADR 只定"不把块格式逻辑散进片段"的边界。

## 后果

### 正面

- P3 接 Metal / CUDA 时，同原语多实现经注册表键挂载，第二套后端不回改算子、模型与调度；双后端不会分叉出私有设备假设。
- 签名解析规则只有一份，构建期校验与运行期装载不会漂移；参数维度有契约落点，错配在装载期而非编译 / 运行后暴露。
- 缓存能区分同原语的不同内核实现，特化产物复用路径后期不必重搭。
- 标量参考保持数值事实源，片段与参考对拍有唯一口径。

### 负面

- 注册表键与校验形状在 P0 是"编译期类型 + 文档契约"，没有真实后端实现挂载；本轮不产出可运行内核。
- 片段保留五份外壳，短期代码密度略低于单一模板生成；换取的是 P3 手写指令集特化的空间。

### 中性

- `arch` 字段是登记标签，不产生热路径分发；选择算法属 P1/P2 plan 层。
- 一致性校验只比对文本同构，不校验跨设备数值等价（数值等价仍由 witness 对拍守）。

## 不做

- 本轮不实现注册表运行时选择、不落地后端内核、不引入线程池或 SIMD（P1/P3）。
- 不补 L0 五条原语（`mma` / `scan` / `exp2` / `rcp` / `atomic`）的片段文本；它们随 P1 首条对应真实内核一起补片段与见证。
- 不造通用 IR、不引 `syn` / `quote` / `proc-macro2`；热路径不出现 `enum` / `dyn` 运行时分发。
- 不把量化常数、零点、种子压进配置；不设第二套设备能力闭集。

## 备选方案

- **注册表放进新独立 crate**：拒绝。P0 没有后端实现可挂，新 crate 只会多一层仪式；类型契约随 P1 后端边界 crate 落地时再拆。
- **现在就把五份片段压成模板生成器**：拒绝。算法尚未分化，模板化会提前约束 P3 手写内核空间；先做一致性校验，分化后再上模板。
- **片段自行声明类型语义**：拒绝。类型事实源必须是档案 `provides`，否则协商结论与片段口径可以同时为真却指向不同实现（`lib.rs:93-97` 已述）。

## 修订

- 2026-11-15：初稿，定注册表七元组、挂载分离、片段契约、复用原则、解析单源化、缓存身份字段；实现随 P1/P3。
- 2026-11-15：§6 缓存身份字段形状落地 [`CacheKey`]：`impl_name`（参与展开片段的实现名并集）、`block`（标量记 `1`），`arch` 已在，三者进指纹；缺绑定类别归 `Invalid` 并加守护测试。片段参数类型签名交叉校验仍随 P1 首条真实内核落地。
- 2026-11-17：§1 七元组键落地类型形状 [`prof::atom::KernelKey`]：`(prim, impl_name, dtype, space, lanes, arch, block)`，复用 `Prim`/`DType`/`Space` 闭集；`lanes`/`block` 为 0 归一为标量 `1`，`signature()` 按 ADR 键序渲染。键只承载身份、不持有可执行句柄；`Provide` 集合/区间到单点键的拆分口径、`KernelKey → 条目句柄` 登记表与运行时选择仍随 P1 首条真实内核落地，本阶段不建注册表 Map、不接分派。
- 2026-11-20："中性"里"一致性校验只比对文本同构"补一条**语义**校验：`prim` 的 `a_reduction_fragment_must_fold_through_func` 要求 `reduce` 片段必须经 `$func` 折叠。文本判定按 `(prim, impl)` 分组，而 `scalar_loop` / `shfl.bfly` / `sub_group_reduce` / `vcreduce` 是四个不同的实现名，各组只有一个成员——于是 `ascend/reduce.cpp` 与 `intel/reduce.cl` 的 `($0) = ($1)` 一直"同构通过"，实际只在归约长度 1（`gemv` 的 `&v, 1, 1`）时正确，对 `softmax` 的 `GMAX` 与 `reduce_*` 静默取首元素。两处已改成 `$func($1, $2, $3)`；`intel` 的空 `[compile].preamble` 同时补上 `_cutile_*_f32` 软件接口，否则片段改对之后无从定义。
