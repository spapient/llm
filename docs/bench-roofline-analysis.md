# 算子基准的 roofline 定位（P1）

- 版本：v1.0
- 日期：2026-11-16
- 主机：Apple M5 Pro / macOS 27.0.1 (26A434) / rustc 1.100.0-nightly (0dfb098f3 2026-08-31)
- 数据来源：`target/bench-report/macos-aarch64/*.json`（由 `cargo test -p llm-benches --test regress` 生成）
- 配套文档：[`engine-benchmark-roadmap.md`](engine-benchmark-roadmap.md)（§2.1 可证伪条件、§4 性能测量、§5 基准 harness、§6 P1）、[`lld.md`](lld.md)（E6 roofline 口径、E7 带宽门槛）

## 一、这份文档回答什么

`#63` 是「基准实测 + roofline 瓶颈定位」。实测部分已经在 `crates/benches` 里跑起来（7 条 criterion 基准、`tools::regress` 门禁、macos-aarch64 基线）；本文补的是后半部分：**每条基准的上界是多少、实测达成了多少、瓶颈落在哪一侧**。文中每个数字都能从归档 JSON 里读出来，也能在本机重跑复现。

结论先写在这里：

1. 七条基准**没有一条**达到 85% 的带宽门槛（`docs/lld.md` E7）。最接近的是 `gemv_f32`（36%），最远的是 `attention_f32`（0.15%）。
2. 「四算子内存型」如果指**算术强度 <1 flop/字节**（`softmax` 0.19、`rmsnorm` 0.25、`rope` 0.50、`silu` 0.12），数据支持；如果指**实测卡在带宽上**（1%–15%），数据不支持。两种说法混用会推出「扩容存原语」的错误结论。
3. 因此「P1 不扩逐元素 / axpy 原语」在现有证据下成立：没有一条基准顶到搬运上界，新增搬运原语无法解释任何一条差距；能缩短差距的是逐元素算子的向量化与超越函数实现、`gemv` 的访存模式、`attention` 的分块与短循环。要推翻这个判断，需要一条达成率 ≥85% 的基准，或采样证据显示时间确实花在内存等待上。

## 二、口径：上界的分子与分母都不是手写的

| 部分 | 来源 | 为什么不能换 |
|---|---|---|
| 分子（至少搬多少字节、算多少次） | `nn::Bounds::of_context`，由 `op` 的算子语义表（求和表达式 + 操作数位宽/方向）推出 | 换掉就成了手写常数，算子一改公式就漂移；`nn` 明确不拥有第二份流量公式 |
| 分母（每秒能搬多少字节） | `criterion/mem_stream.rs` 的三档实测，读 / 写分开 | 厂商峰值只是规格，不是这台机器测得到的速率；`lld` E6 把「仅有未验证的峰值规格」判为不可计算 |
| 档位（拿哪一档的分母去比） | 工作集大小：≤64 KiB 记 `l1`、≤2 MiB 记 `l2`、其余记 `dram` | 拿 L1 里的往返去比主存带宽，达成率就没有意义 |
| 达成率 → 瓶颈分类 | ≥85% 记 `bandwidth`，否则记 `not-bandwidth` | 与 `lld` E7 的带宽门槛同一口径；低于门槛只否定「带宽主导」，不猜是算力还是延迟 |

三档是三个**测量点**（16 KiB / 1 MiB / 64 MiB），不是猜出来的缓存容量；档与档之间留了四倍余量。机型、系统、工具链与上界一起登记在 `crates/benches/tests/regress.rs` 的 `HOSTS` / `CEILINGS` 里——换芯片、换系统或换编译器，就必须重新登记，未登记的主机在 CI 上直接跳过判定。

本机三档实测上界（`mem_stream`，2026-11-16）：

| 档位 | 工作集 | 读 | 写 |
|---|---|---:|---:|
| `l1` | 16 KiB | 143,601 MB/s | 121,013 MB/s |
| `l2` | 1 MiB | 129,406 MB/s | 130,968 MB/s |
| `dram` | 64 MiB | 87,265 MB/s | 132,410 MB/s |

读侧用无符号整数异或归约（浮点求和默认不可重排，会把循环串行化成加法延迟），写侧用 `fill`。两者都是**单线程、同代码形态**下能跑出的最快搬法，不是 SIMD 理想值，也不是厂商峰值——所以下面所有达成率的含义是「离这台机器单线程能做到的最好还有多远」，不用于对外宣称硬件利用率。

## 三、七条基准的定位

| 场景 | 档位 | 读 B | 写 B | flops | 强度 flop/B | 上界 ns | 实测 ns | 达成率 | 瓶颈侧 | 实测算力 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---|---:|
| `gemv_f32/decode_1x4096x4096` | dram | 67,125,248 | 16,384 | 33,554,432 | 0.50 | 769,209 | 2,134,594 | 36% | read | 15.7 GFLOP/s |
| `attention_f32/flash_decode_128x64` | l2 | 98,304 | 32,768 | 2,146,304 | 16.38 | 760 | 504,561 | 0.15% | read | 4.3 GFLOP/s |
| `gemm_f32/prefill_256x256_k8` | l2 | 16,384 | 262,144 | 1,048,576 | 3.76 | 2,002 | 16,599 | 12% | write | 63.2 GFLOP/s |
| `rmsnorm_f32/decode_1x4096` | l1 | 49,152 | 16,384 | 16,384 | 0.25 | 342 | 2,304 | 15% | read | 7.1 GFLOP/s |
| `softmax_f32/decode_1x4096` | l1 | 49,152 | 16,384 | 12,288 | 0.19 | 342 | 8,337 | 4% | read | 1.5 GFLOP/s |
| `silu_f32/decode_1x4096` | l1 | 16,384 | 16,384 | 4,096 | 0.12 | 135 | 3,287 | 4% | write | 1.2 GFLOP/s |
| `rope_f32/decode_1x4096` | l1 | 16,384 | 16,384 | 16,384 | 0.50 | 135 | 9,487 | 1% | write | 1.7 GFLOP/s |

`attention` 的达成率是 0.15%，报告按整数口径归档为 0；`mflops_per_s` 字段是报告里的同一组实测算力。

### 3.1 `gemv_f32`：全表最接近带宽，但仍有 2.8× 余量

67.1 MB 权重、2.13 ms 实测 → 读速率 **31.4 GB/s**，本机 `dram` 读上界 87.3 GB/s。也就是说「把权重读进来」这件事本身只需要 769 µs，实测花了 2.13 ms。这条 kernel 在本机口径下的收益上限就是 **2.78×**，而且要靠访存连续、可预取、不在内层反复做边界检查去拿——不是靠再加一个搬运原语。

「gemv 带宽主导」这个说法在 36% 的达成率下**不成立**：它离带宽最近，但没有顶到带宽。要说它带宽主导，需要一条达到 85% 的测量，或采样证据显示时间确实停在等内存上。

### 3.2 `attention_f32`：差 663×，问题不在搬运

131 KB 工作集、上界 760 ns、实测 504,561 ns。131 KB 的搬运即使按 `l1` 档的写侧上界 121 GB/s 算也只有 1 µs 量级，解释不了 505 µs 的差距；同时它的算术强度 16.4 flop/字节是全表最高。`flash_reference` 每行一次 `vec!` 分配、每个 score 两次 `exp`、内层 `d` 长循环逐元素读 `v`——代价在短循环与逐 score 运算上。结论很直接：给这条加搬运优化不会让它变快。

### 3.3 `gemm_f32`：写侧上界，算力已经最高

prefill 256×256、K=8：读 16 KB、写 256 KB，上界由写侧决定（262,144 B ÷ 131.0 GB/s ≈ 2.0 µs），实测 16.6 µs。实测算力 63.2 GFLOP/s 是全表最高，说明这条是「算」为主的 prefill 形状。要提速只能改内层循环（寄存器分块、向量化、减少重复地址计算），减流量没有用。

### 3.4 `rmsnorm_f32` / `softmax_f32`：65 KB 全在 L1，贵在逐元素

两者工作集都是 65,536 B，上界 342 ns；实测 2,304 ns 与 8,337 ns（28.4 GB/s 与 7.9 GB/s 的搬运速率）。两趟 / 三趟遍历本身在 L1 上只值 0.34 µs，差距来自每一趟的标量逐元素处理；`softmax` 多一趟 `exp`，达成率因此比 `rmsnorm` 低一档。这里的提升手段是向量化与 `exp` 实现，不是扩容存原语。

### 3.5 `rope_f32` / `silu_f32`：全表最远离带宽

32,768 B、上界 135 ns，实测 9,487 ns 与 3,287 ns。两条都是「每元素一次超越运算」的形态（`rope` 每对元素算角度与三角，`silu` 每元素一次 `exp`）；上界只相当于实测耗时的 1.4%（`rope`）与 4.1%（`silu`），也就是说在这两条上谈内存优化，收益上限不到 4%。

## 四、这份定位能推出什么、不能推出什么

**能推出：**

- 七条里没有一条达到 85% 带宽门槛，因此按 `lld` E7 的口径，**没有一条可以被称为「带宽主导」**。
- 各条的收益上限（本机口径）是可算的：`gemv` 2.8×、`attention` 663×（算术侧而非内存侧）、其余四条的内存侧收益都 ≤15%。
- 扩逐元素 / axpy 原语在现有证据下没有收益空间：没有一条基准顶到搬运上界。

**不能推出：**

- **不能**把达成率当成硬件的带宽利用率对外宣称：分母是同代码形态的单线程搬法，不是峰值。
- **不能**由达成率区分「算力瓶颈」与「延迟瓶颈」：那需要 prof 采样，本仓目前没有 CPU 侧采样证据。低于 85% 只够写 `not-bandwidth`。
- **不能**把这些数字当成 kernel 性能：被测的是 `op` 里的标量参考实现，它们不是将来 kernel 的形态。
- **不能**跨机比较：换机型 / 系统 / 工具链必须重新登记基线与上界。

## 五、复跑

```bash
# 三档读 / 写上界（roofline 的分母）
cargo bench -p llm-benches --bench mem_stream

# 七条算子基准（roofline 的实测侧）
cargo bench -p llm-benches

# 判定 + 归档：target/bench-report/<host>/*.json
cargo test -p llm-benches --test regress
```

`crates/benches/tests/regress.rs` 是唯一的判定点：基线、上界、主机档案都在那里，未建档的主机（例如 CI 的 `linux-x86_64`）会跳过判定而不是拿别的机器的数判。
