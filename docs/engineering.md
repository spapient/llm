# 工程标准 — 工作流、错误、命名、公开 API、测试与性能

状态: 拟定

范围: llm/ 工作区内所有 crate、二进制、集成测试、示例与基准，以及涉及开发、重构、调试、测试、优化、错误处理、命名、公开 API 设计与文档的变更

读者: 工程师、评审者、维护者、AI 编码代理

---

## 1. 引言与目的

本文档是 llm/ 工作区工程实践的单一权威来源，合并了工作流、错误处理、命名、公开 API、测试与性能六项工程标准，以及两项测试决策记录。原分散文档之间的相互引用已全部消除，本文档自包含。

各项标准的目的如下。

工作流：定义 llm/ 工作区内工程任务的强制执行流程，使每个变更足够小以便理解、足够精确以便评审、足够严谨以便验证。开发被视为受控的工程过程，而非一连串代码生成操作。每个任务必须确立：正在解决什么问题；涉及哪些既有契约与依赖；什么可以改变、什么不可以；如何确立正确性；如何验证变更；什么证据支撑完成声明；还有什么未解决。工作流同样适用于人类贡献者与 AI 辅助开发。指导原则是：

> 先理解，窄计划，最小变更，独立验证，如实报告。

错误处理：目标不是简单地防止 panic，而是使失败显式、可诊断、在适当时候可恢复、并跨 crate 边界保持一致。错误处理必须保留以下条件之间的区别，它们不可互换，不得被折叠成通用错误、静默转换为成功或以任意回退行为处理：

- 无效外部输入。
- 无效内部状态。
- 不支持的功能。
- 值的预期缺失。
- I/O 与序列化失败。
- 后端执行失败。
- 资源耗尽。
- 取消与超时。
- 编程缺陷与不变量破坏。

命名：命名是一份契约。读者必须能从动词推断函数做什么、从名词推断返回什么，而无须阅读函数体。同义词漂移是本标准要防止的失败模式：两件相同的事用两个不同动词，会迫使每个读者重新推断意图。

公开 API：公开 API 是长期工程承诺。每新增一个公开类型、trait、函数、方法、字段、泛型参数、特性开关与行为保证，都会增加未来实现必须保持的约束数量。项目因此优先考虑：最小的公开表面积；显式所有权与错误行为；组合优先于类继承式抽象；默认静态分发；稳定接口与实现细节的清晰分离；兼容性感知的演进；可测试的契约而非未记录假设；无不必要抽象或投机式扩展性。公开 API 必须有意识地设计；仅因另一个 crate 当前需要访问就使类型或模块公开，不足以证明把它作为受支持外部接口暴露是合理的。

测试：测试不是实现之后的最后一步，而是设计过程的一部分，是正确性、兼容性、数值行为与性能声明的必需证据来源。目标包括：在显式契约边界验证行为；在回归跨 crate 传播前检测它们；独立于实现细节验证数值正确性；检验格式错误输入、边界条件与失败路径；通过自动检查保持架构边界；为性能测量建立可复现证据；使每个完成的变更可独立测试；保持测试确定、聚焦、可维护且在重构中有用。通过的测试套件是已测试行为的证据，不是每个可能执行都正确的证明；测试声明必须与证据的覆盖与强度成比例。

性能：目标是实现可测量、可复现的性能改进，同时不牺牲正确性、数值完整性、架构简洁性、安全性与可维护性。性能是系统属性，取决于不止单个函数或算子的速度。相关因素包括：算法复杂度；张量布局与内存访问模式；分配与缓冲复用；数据移动与拷贝；缓存局部性；CPU 向量化与并行执行；线程调度与同步；算子分发开销；模型架构与执行结构；批大小与序列长度；输入输出处理；编译设置与目标硬件；资源争用与工作负载特征。只有局部优化的收益与预期工作负载相关且其成本被理解时，它才有价值。

本文档给出目标标准，不声明工作区现有实现已经符合。一致性与采纳的状态见本文《一致性与采纳》章节。

## 2. 规范用语

术语 MUST、MUST NOT、SHOULD、SHOULD NOT、MAY 表达工程要求：

- MUST / MUST NOT：强制的工程约束。
- SHOULD / SHOULD NOT：默认规则；例外须有明确的技术理由。
- MAY：适合实现的可选行为。

MUST 级要求仅在经过明确、可评审的架构决策后方可豁免；该决策必须记录其范围、理由、风险与验证策略。在命名标准中，豁免须记录需求 ID、原因、降级方案与作用范围。

本文档中的代码片段是说明性的，不构成工作区的实际实现；真实的类型、变体与错误契约由其对应 crate 拥有。

## 3. 非协商规则

每个任务必须遵守以下规则。这些规则适用于同步与异步代码、CPU 与加速器后端、推理、训练、序列化、checkpoint 操作与服务接口。

### 3.1 通用工程规则

1. **修改前先理解。** 在修改 crate 之前，阅读其职责、清单、公开 API、相关实现、测试与依赖关系。不得仅凭文件名或目录结构推断实现细节。
2. **保持依赖方向。** 不得引入依赖环或绕过既有的 crate 边界。每条新的工作区依赖边都需要明确理由。
3. **一次提交只完成一个可独立测试的阶段。** 无关的功能、重构、格式化与优化不得仅为减少提交数量而合并。
4. **文档必须与事实一致。** 设计提案不是实现；未执行的测试不是通过的测试；未测量的优化不是已证实的改进。
5. **保持变更可评审。** 不得把行为变更隐藏在仅格式化的提交中；不得修改生成文件或无关文件。
6. **每个生产行为必须有适当的验证策略；每个可合理复现的缺陷修复必须包含回归测试；每个实现阶段应足够小以便独立验证。**
7. **变更不得仅因为它能编译就被视为完成。** 必须诚实报告实际执行了什么。

### 3.2 正确性与安全

8. **显式错误处理。** 生产运行期失败必须通过显式错误路径表示与传播；运行期错误不得以 `panic!()`、`unwrap()` 或 `expect()` 处理。
9. **不得静默丢弃或把错误转换为成功形态的值。** 必需的持久化、状态更新与安全检查的错误不得被忽略。
10. **预期缺失用 `Option<T>` 等适当表示**，而不是错误或伪造默认值。
11. **错误类型表达稳定的语义类别**，而不依赖人类可读字符串。
12. **每个 crate 拥有其自身抽象与不变量的错误**；错误仅在有意义的抽象边界转换；错误转换不得丢失语义区别（无效输入不得变成内部服务器错误、资源耗尽不得变成无效输入、取消不得变成成功、损坏的持久状态不得变成普通的缺失值、不支持功能不得变成无关的后端失败）。
13. **错误处理不得掩盖被破坏的不变量或让无效状态看似有效。** 无效的外部输入是可恢复错误；内部不变量破坏可能表示编程缺陷，不得伪装成普通用户输入失败。
14. **禁止 unsafe 代码**（由工作区 lint 配置 `unsafe_code = "deny"` 强制）。不得引入任何形式的 unsafe 构造，也不得放宽该约束。若某项需求看似需要 unsafe，应以安全 Rust 重新设计，或报告该限制。
15. **请求态隔离。** 模型权重对象不得包含请求级可变状态；推理变更必须保持共享模型数据与每请求执行状态之间的分离。
16. **取消与超时不得被视为普通成功。** 资源限制应在可能超限的操作之前检查。

### 3.3 性能与证据

17. **先建立正确性，再接受优化。** 未满足正确性契约的实现不得作为优化被接受。
18. **每个新算子必须至少包含一个基准。**
19. **性能改进必须由可比较的测量支撑。** 不得仅凭代码外观或直觉声称性能提升；测量噪声不得被呈现为已确认的改进。
20. **基准必须足够标明工作负载与环境以解释结果；优化必须保持已记录的语义契约；性能测试不得静默替代正确性测试。**
21. **优化复杂度必须由经测量的收益或明确的架构需求来证明其合理性。**
22. **当局部优化可能影响整体时，必须考虑端到端性能。** 性能敏感的变更必须包含回归考量。
23. **失败、无结论或不可用的测量必须如实报告。**
24. **优化不得引入被禁止的 crate 依赖或循环依赖。**

### 3.4 测试

25. **测试不得依赖执行顺序、墙钟计时、网络可用性或不受控的外部状态**，除非测试明确针对该依赖。
26. **数值测试必须使用适当的参考与已记录的容差。**
27. **当失败语义属于契约的一部分时，测试必须覆盖失败行为。**
28. **不得仅为让错误实现通过而弱化测试。**
29. **基准不得用于替代正确性测试。**
30. **架构与依赖约束应尽可能自动强制。**
31. **所有报告的结果必须准确描述实际执行的内容。**

## 4. 工作流与执行协议

### 4.1 任务分类

执行前，按主要目标对任务分类。主要类别决定主要验收标准，每个受影响的次要类别补充额外要求。分类不得用于规避必需的测试。

| 任务类型 | 主要关注点 | 必需证据 |
| --- | --- | --- |
| 文档 | 准确性与一致性 | 跨文档评审 |
| Bug 修复 | 复现与防止回归 | 尽量先失败后通过的测试 |
| 新功能 | 契约与行为 | 验收测试 |
| 新算子 | 数值正确性与边界 | 参考测试与基准 |
| 重构 | 保持行为 | 相关回归测试 |
| 架构变更 | 依赖与所有权完整性 | 依赖图与架构评审 |
| 性能优化 | 可测量的改进 | 可比较的基准结果 |
| 安全敏感变更 | 内存与资源正确性 | 安全论证与针对性验证 |
| 依赖更新 | 兼容性与供应链风险 | 构建、测试与依赖评审 |
| 发布准备 | 集成与可复现性 | 全部适用的发布检查 |

### 4.2 执行生命周期

每个实现任务都遵循以下生命周期。若某个验证步骤失败，回到最小相关的更早阶段。

```text
Request
  |
  v
1. Understand the objective
  |
  v
2. Inspect repository and dependencies
  |
  v
3. Establish baseline
  |
  v
4. Write execution plan
  |
  v
5. Define acceptance criteria
  |
  v
6. Implement the smallest change
  |
  v
7. Validate behavior and boundaries
  |
  v
8. Review diff and architecture
  |
  v
9. Record evidence and limitations
  |
  v
10. Commit one completed stage
```

当失败使下一阶段所需的假设失效时，不得继续添加功能。并非每个仅文档的变更都需要编译整个工作区；验证深度必须与变更相称，但省略检查的理由必须清晰。

### 4.3 阶段 A — 理解目标

在触碰文件之前，写出简明的问题陈述，必须识别：当前问题或缺失的能力；预期可观察的结果；受影响的子系统；相关架构约束；明确的非目标。

任务的完成无法被客观判定时，说明其规格不足。

区分需求与假设：将相关信息分类为已确认（由仓库内容、测试或明确需求支撑）、假设（看似合理但未验证）、未知（需要勘察或决策）、超出范围（有意排除）。不得静默地把假设转换为实现需求。若某个缺失的决策可能改变正确性、安全性、公开 API 行为或依赖方向，则在实现前解决它。

定义最小有用结果：优先选择窄而可观察的结果，而非宽泛的目标。例如，将"提升推理性能"替换为"为现有 CPU decode 路径建立可复现基线，识别其主导的实测成本，并在不改变运行期行为的前提下报告结果"。

### 4.4 阶段 B — 仓库勘察

在修改目标 crate 之前，检查其实际实现。

至少检查：仓库级 AGENTS.md；根 Cargo.toml；rust-toolchain.toml 与相关构建配置；目标 crate 的 Cargo.toml；目标 crate 的公开入口与模块结构；相关源码实现；现有测试与基准；直接工作区依赖；相关调用方与下游消费者；现有文档与架构决策。对于跨 crate 变更，检查每一个受影响的 crate，而不是把发起 crate 视为全部范围。

建立实际依赖图，使用 Cargo 元数据与依赖树检查识别真实图：

```sh
cargo metadata --workspace --format-version 1
cargo tree --workspace
```

按需检查 normal、build、development、optional 与 feature 相关的关系。不得因为某依赖只出现在清单中而假定它无害：其特性激活与传递闭包可能改变实际架构。

编辑前检查工作树：

```sh
git status --short
git diff --check
git diff
```

这些命令帮助识别现有用户变更与当前差异中的格式问题。不得覆盖、丢弃或重新格式化无关的用户修改。未经明确授权，不得使用破坏性 Git 操作来获得干净的工作树。

勘察输出必须确立：目标 crate 与其负责的职责；相关公开契约；现有依赖路径；重要不变量；现有测试与基准；潜在回归风险；可能阻塞实现的未知项。若仓库不可用，明确说明未进行源码级勘察。

### 4.5 阶段 C — 建立基线

在改变行为之前，确定相关起始状态。

正确性基线：运行最窄的相关现有测试；对于影响共享契约、公开 API 或多个 crate 的变更，相应扩大测试范围。记录变更前已存在的失败。预先存在的失败不得自动归因于当前任务。

构建基线：验证相关工具链与构建配置。在范围需要时使用工作区检查：

```sh
cargo check --workspace --all-targets
```

对于较小的变更，迭代期间针对性检查可能足够，完成前再运行更广泛的检查。

性能基线：对于性能工作，在优化前建立基线，记录：机器与 CPU 信息；操作系统；Rust 工具链与相关编译器设置；构建 profile 与启用的特性；输入维度与工作负载；预热与测量流程；样本数量与统计摘要；相关时的内存消耗。若无法收集可靠基线，任务仍可作为探索性工作继续，但不得声称性能改进。

基线报告：记录每项相关检查是 通过 / 失败 / 未运行 / 阻塞。不得因为后续命令通过就把失败的命令描述为成功。

### 4.6 阶段 D — 编写执行计划

每个非平凡任务在实现前必须有书面计划，必须指定：目标；目标文件与 crate；预期行为变更；预期依赖变更；相关不变量；测试策略；验收标准；适当的回滚或恢复考量。

变更预算：定义最小的合理变更集。优先：每个阶段一个职责；窄的公开 API 变更；复用既有抽象；局部化修复；显式所有权转移。避免：无关清理；仓库级重命名；无证据的广泛模块重组；过早泛化；同时替换多个基础抽象。当出现新证据时计划可以改变；任何实质的范围变化必须在继续前记录。

依赖变更预算：若任务引入新的依赖边，说明：为什么需要该边；哪个 crate 拥有所需能力；为什么现有契约不足；该边是否改变依赖图；如何检查环与禁止边。若提议的变更需要反向依赖，停止并重新设计接口。

### 4.7 阶段 E — 定义验收标准

验收标准必须可观察、可测试。

弱的："tensor 实现更健壮了"。

强的：形状乘法检测溢出；无效维度返回已记录的错误；现有有效输入保持其行为；边界测试覆盖零、最小与支持范围内的溢出相关情形；相关测试在配置的工具链下通过。

验收类别（选择相关类别）：API 行为；数值正确性；错误传播；依赖方向；所有权与生命周期；并发与请求隔离；资源限制；序列化兼容性；性能测量；文档一致性。

否定要求：明确说明什么不得改变。例如：无新运行期依赖；无公开 API 变更；无额外 unsafe；不改变模型权重布局；不改变推理输出语义；不改变无关格式。否定要求很重要，因为局部正确的实现仍可能违反系统级约束。

### 4.8 阶段 F — 实施最小正确变更

实现必须遵循已批准的计划。

保持既有契约：在改变公开接口之前，识别所有调用方及其假设。不得静默改变所有权行为、错误语义、形状约定、数值容差、取消行为、资源生命周期保证。若契约必须改变，将其作为明确的 API 或架构任务处理。

优先组合：当现有窄 trait 与具体类型满足需求时使用它们。当具体实现足够时，不要添加泛型框架。除非运行期选择或其他具体需求证明其合理性，否则不要添加运行期多态。不要创建吸收无关状态的通用上下文对象。

错误处理见本文《错误处理与失败语义》章节。unsafe 变更：工作区完全禁止 unsafe 代码，不得引入新的 unsafe 代码。若某项需求看似需要 unsafe，以安全 Rust 重新设计，或报告该限制，而不是放宽禁令。

保持变更可评审：不得把行为变更隐藏在仅格式化的提交中；除非构建需要或计划明确包含，不得修改生成文件或无关文件；持续评审差异，而不是等到大变更结束时。

### 4.9 阶段 G — 递进范围验证

验证应从廉价、针对性的检查开始，并随变更影响扩大。

- **级别 1 局部反馈：** 编译受影响的代码；运行针对性单元测试；检查已变更 Rust 代码的格式；检查局部差异。
- **级别 2 契约验证：** 测试有效与无效输入；验证已记录的错误行为；测试相关形状与数值边界；验证所有权与生命周期假设。
- **级别 3 集成验证：** 编译受影响的依赖 crate；运行相关集成测试；验证公开 API 兼容性；在相关时检查依赖方向与特性组合。
- **级别 4 工作区验证：** 对于影响广泛的变更，运行适用的工作区检查：

```sh
cargo fmt --all -- --check
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

这些命令是提议的基线；实际工作区可能需要特定特性、平台或工具链的调整。只有命令真正运行并观察到结果，检查才算完成。

- **级别 5 专项验证：** 在适用时添加专项检查：依赖边界变更的架构检查；计算算子的数值参考测试；推理变更的请求隔离测试；持久化变更的序列化兼容性测试；新算子与性能工作的可复现基准。

更广泛的测试套件通过，不消除必需的专项测试。

### 4.10 阶段 H — 评审差异

在宣布完成之前，像独立评审者那样评审最终差异。提出以下问题。

**正确性：** 变更是否解决所述问题？边界条件是否覆盖？错误路径是否显式？整数溢出、无效布局或资源耗尽是否会导致错误行为？数值假设是否已记录？

**架构：** crate 职责是否保持？是否引入了依赖环？公开接口是否不必要地宽？动态分发是否有理由？低层 crate 是否获得了高层知识？

**状态与所有权：** 可变状态是否由正确对象拥有？两个请求是否会意外共享可变执行状态？取消与提前终止是否处理？失败时资源是否释放？

**可维护性：** 解决方案是否比替代方案更简单？新抽象是否必要？不变量是否在代码中可见？文档是否与实现一致？无关变更是否已移除？

**证据：** 相关检查是否执行？基线失败是否与新失败区分？基准比较是否有效？局限是否被诚实陈述？

任何未解决的正确性、安全性或架构缺陷必须修复，或明确报告为阻塞完成。

### 4.11 阶段 I — 性能工作

性能优化需要其自身的执行纪律。

优化流程：1. 建立正确性。2. 测量基线。3. 从证据识别瓶颈。4. 形成具体假设。5. 实施一个有意义的变更。6. 重跑正确性测试。7. 在可比条件下测量。8. 检查变异与回归。9. 记录结果。

使用本文《性能工程与基准》章节定义的性能状态词汇。不要用"优化"作为"改变"的同义词。

报告不止一个数字。在相关时报告：基线与候选结果；工作负载与环境；样本数；中位数或其他合适摘要；变异；绝对与相对差异；内存影响；已知局限。不要只挑选有利的工作负载，而忽略目标工作范围内的重大回归。

### 4.12 阶段 J — 文档与变更记录

当实现变更影响以下内容时，在同一阶段更新文档：公开 API；crate 职责；依赖关系；错误语义；资源所有权；支持的格式；数值行为；性能声明。对于重大架构决策，添加决策记录。

文档必须区分已验证行为与预期行为。不得声称支持未实现的后端、算子、文件格式或执行模式。

### 4.13 失败与恢复协议

当命令或测试失败时：1. 保留确切的失败信息。2. 判断失败是否早于本次变更。3. 识别最小受影响范围。4. 尽可能复现失败。5. 修复原因而非抑制症状。6. 适当时添加回归测试。7. 重跑失败检查与相关验证。8. 明确报告剩余失败。

不得：仅为获得通过的套件而删除失败测试；在没有已记录契约变更的情况下弱化断言；忽略揭示相关缺陷的编译器警告；把错误转换为成功形态的输出；因为无关检查通过就声称成功；隐藏环境限制。

若失败超出任务范围且无法在其中安全修复，将其记录为阻塞项或后续任务。

### 4.14 提交纪律

每个提交必须完成一个可独立测试的阶段。一个提交应回答一个问题："这个变更确立了哪一个单一的、连贯的工程结果？"

可接受的阶段示例：定义并测试带检查的 tensor 尺寸运算；添加一个 CPU 算子并附正确性测试与一个基准；引入请求级 KV Cache 所有者与隔离测试；添加依赖图架构检查；记录一个已批准的公开 API 契约。

不可接受的组合阶段示例：添加多个算子、重新设计 tensor API 并优化 SIMD；重写推理、更新 checkpoint 格式并重构 CLI；在工作区重新格式化的同时改变无关的运行期行为。

一个阶段在确立同一连贯结果所必需时，可以包含多个文件与测试。不得在会使中间提交无效、不安全或误导时人为拆分变更。

**提交信息：** 应传达受影响领域与已完成结果，例如：

```text
tensor: validate shape size overflow
```

信息必须描述实际变更，而不是预期的未来功能。

**提交前检查清单：** 确认预期文件是唯一被修改的文件；检查已暂存的差异；运行适用的验证；确认未包含密钥、生成产物或无关变更；记录未解决的局限；确认提交代表一个已完成的阶段。除非实际创建了提交，否则绝不声称提交存在。

### 4.15 AI 辅助开发协议

AI 编码工具必须遵循与人类贡献者相同的仓库规则。

**编辑前：** 助手必须检查相关仓库说明、清单、源文件、测试与依赖边界。不得虚构文件、公开 API、测试结果、基准测量或现有实现细节。

**编辑期间：** 助手必须：在已批准的变更范围内工作；优先最小补丁；保留无关的用户修改；避免引入未请求的依赖；避免投机式重构；分离独立阶段；解释实质性的架构决策。

**完成前：** 助手必须：检查最终差异；在执行能力可用时运行适用检查；准确报告运行了哪些检查及其结果；区分已验证事实与假设；识别未测试的行为与环境阻塞；没有证据时避免声称文件已修改、测试已通过或提交已创建。若仓库访问或执行能力不可用，助手可以提供提议的补丁或文档，但必须标明其未验证。

**范围扩张：** 若勘察揭示更大的架构问题：1. 识别问题。2. 解释其影响。3. 判断它是否阻塞当前任务。4. 将无关变更排除在当前阶段之外。5. 适当时提出单独任务。不要把每个局部修复变成未经请求的仓库级重新设计。

### 4.16 完成报告

每个已完成的工程任务必须产出一份简明的完成报告，使用以下结构：

- **目标：** 任务意在确立什么。
- **变更：** 哪些文件和契约发生了改变，以及为什么。
- **架构：** 哪些 crate 边界和依赖受影响。
- **验证：** 对每项相关检查记录：确切的命令或测试；执行状态；结果；相关失败细节。
- **性能：** 如适用，提供基线与候选测量、环境、方法与局限。若未测量，说明未确立性能改进。
- **安全与资源：** 描述适用的所有权与资源生命周期考量。
- **局限：** 列出未解决的问题、跳过的检查与已知不支持的行为。
- **提交：** 仅在确实创建了提交时给出实际提交标识符。

## 5. 错误处理与失败语义

### 5.1 错误处理模型

工作区应使用分层错误模型。

```text
External input / caller
        |
        v
Boundary validation
        |
        v
Domain operation
        |
        v
Crate-local implementation
        |
        v
Backend / filesystem / external dependency
```

每一层有不同职责。

**边界校验：** 边界校验外部提供的值，并将底层失败转换为适合其公开契约的错误。示例：无效张量维度；格式错误的模型配置；不支持的模型标识符；无效的 tokenizer 输入；无效的 checkpoint 元数据；无效的 HTTP 请求参数。边界校验在可能时应先拒绝无效输入，再执行昂贵或不可逆的工作。

**领域操作：** 领域操作以领域术语表达失败。示例：张量形状与操作不兼容；请求的模型特性不受支持；checkpoint 不包含所需参数；优化器配置无效；请求的推理操作超出其声明预算。领域错误应保持独立于 CLI、HTTP、文件系统呈现与其他应用特定协议。

**基础设施与后端操作：** 基础设施层将底层机制的失败转换为其调用方有意义的错误。示例：文件读写；内存分配或缓冲保留；CPU 内核执行；设备初始化；后端同步；序列化与反序列化。基础设施错误在这样做有意义且安全时，应保留原始源错误。

**应用边界：** 应用层决定如何呈现或处理错误。示例：CLI 打印简明诊断并以非零状态退出；HTTP 服务器将已校验的客户端输入错误映射为适当的客户端响应；训练应用停止当前运行并保留诊断上下文；推理服务返回请求失败而不暴露内部路径或实现细节。应用层不得仅为简化呈现而重新定义底层失败语义。

### 5.2 在 Result、Option 与不变量之间选择

**使用 `Result<T, E>` 表示失败：** 当操作可能以调用方需要区分、报告、恢复或测试的方式失败时使用。

```rust
pub fn validate_shape(
    shape: &[usize],
) -> Result<(), ShapeError> {
    // Validate the shape and return a typed error if invalid.
    todo!()
}
```

真实实现必须执行实际校验，且不得在生产路径留下 `todo!()`。

**使用 `Option<T>` 表示预期缺失：** 当缺失是合法结果而非失败时使用。示例：未提供可选配置字段；查找未找到匹配项且缺失本就是 API 契约的一部分；模型没有可选 bias 张量；调用方请求不存在的可选元数据值。

当 `Option<T>` 会抹去有意义的失败时，不要使用它。例如，可能因文件损坏而失败的 checkpoint 查找不应把每个错误转换为 `None`。

坏：

```rust
let metadata = read_checkpoint_metadata(path).ok();
```

这丢弃了缺失值与读取失败之间的区别。当两者都可能时，优先使用显式表示缺失与失败的契约：

```rust
fn find_metadata(
    path: &Path,
) -> Result<Option<Metadata>, CheckpointError>;
```

具体签名应与实际存储与查找语义匹配。

**不得用伪造默认值掩盖失败。** 以下模式在把真实失败变成表面成功时被禁止：

```rust
// 当回退掩盖真实失败时禁止。
let config = load_config(path).unwrap_or_default();
// 当缺失不是失败的有效替代时禁止。
let tensor = load_tensor(path).ok().flatten();
```

回退仅在回退本身就是领域契约的一部分且不掩盖错误时方可使用。

**区分无效输入与破坏的不变量：** 无效外部输入通常是可恢复错误。内部不变量破坏可能表示编程缺陷或损坏的内部状态，不得伪装成普通用户输入失败。

| 情形 | 预期处理 |
| --- | --- |
| 由有符号外部值表示的负维度 | 在校验时拒绝 |
| 形状维度使支持的尺寸计算溢出 | 返回校验或尺寸错误 |
| 调用方请求不支持的操作 | 返回不支持操作错误 |
| 内部缓冲比已证明不变量要求的更短 | 作为不变量破坏调查 |
| 文件无法读取 | 返回 I/O 相关错误 |
| 可选元数据字段缺失 | 若缺失有效则使用 Option |

生产代码不得把 panic 用作上述任何情形的常规控制流。

### 5.3 错误归属与 crate 边界

每个 crate 应定义其拥有的操作与不变量的错误。crate 不得仅为复用错误类型而依赖应用级 crate。工作区不得引入一个导入每个子系统、迫使无关 crate 相互依赖的大型共享错误枚举。

推荐归属：

| crate 或层 | 典型错误归属 |
| --- | --- |
| tensor | 形状、布局、索引、dtype、尺寸校验 |
| cpu | CPU 内核执行与后端特定失败 |
| autograd | 图构建与梯度计算失败 |
| nn | 层构建与模块配置失败 |
| models | 模型配置、架构支持、参数兼容性 |
| tokenizer | 分词配置、格式错误数据、词表与编码失败 |
| data | 数据集访问、解码与输入管线失败 |
| format | 格式解析、校验与序列化失败 |
| checkpoint | checkpoint 元数据、完整性、兼容性与 I/O 失败 |
| optim | 优化器配置与更新失败 |
| train | 训练编排与运行级失败 |
| infer | 推理编排、生成限制与请求执行 |
| api | 稳定公开契约与边界级校验 |
| serve | 请求校验、服务生命周期与协议转换 |
| cli | 参数校验、命令执行与呈现 |
| testkit | 测试支撑与夹具构建失败 |

该表是归属指南，不是要求创建其中每个错误类型。类型应在表示真实、可区分的失败语义时引入。

**共享错误类型：** 当多个 crate 真正共享同一语义契约时，共享错误类型可以存在。它不得仅为消除少量 `From` 实现或减少 `match` 语句行数而存在。引入共享错误类型前，评审者必须评估：该抽象是否真正共享；新的依赖方向是否被允许；下游 crate 是否需要详细变体；共享类型是否会迫使无关模块相互依赖；共享类型能否在不破坏无关公开 API 的情况下演进。共同的错误词汇有用；对每个子系统实现细节的共同依赖则不然。

**错误归属遵循抽象归属：** 底层 crate 不得返回要求调用方理解无关应用框架的错误。例如，张量操作不应返回 HTTP 响应错误。HTTP 服务器可以把张量形状错误映射为请求响应，但张量 crate 必须保持独立于该呈现决策。

### 5.4 错误类型设计

**优先使用带类型变体：** 错误类型应使有意义的失败类别显式。

```rust
#[derive(Debug)]
pub enum ShapeError {
    EmptyShapeNotAllowed,
    DimensionOverflow,
    ElementCountExceedsLimit {
        requested: usize,
        limit: usize,
    },
    IncompatibleDimensions {
        expected: usize,
        actual: usize,
    },
}
```

该示例说明设计原则；实际变体必须反映 crate 的真实契约。带类型变体使调用方与测试无需依赖显示信息即可区分错误。

**错误变体应表示可操作的区分：** 当区分影响以下至少一项时，创建单独变体：调用方恢复行为；重试资格；API 兼容性；安全处理；诊断或可观测性；可测试的契约行为。不要仅为镜像每个内部函数而创建数十个近乎相同的变体。当调用方需要区分时，不要把语义不同的失败合并进单个 `Other(String)` 变体。

**人类可读信息不是控制流 API：** 错误信息可能因清晰度、本地化或附加上下文而变化。调用方不得使用 `Display` 输出的子串匹配来决定是否重试、返回特定协议状态或选择回退。

坏：

```rust
if error.to_string().contains("timeout") {
    retry_operation();
}
```

优先显式分类：

```rust
match error {
    ServiceError::TimedOut => {
        // Apply the documented timeout policy.
    }
    ServiceError::Cancelled => {
        // Follow cancellation semantics.
    }
    _ => {
        // Handle other failure categories.
    }
}
```

生产代码应使用相关抽象实际拥有的错误类型。

**错误码与稳定公开契约：** 通过公开 API 或线协议暴露的错误，在消费者需要区分时应具有稳定的机器可读码。稳定契约应定义：码；其含义；调用方是否可以重试；该情形表示无效输入还是服务端失败；任何已记录的恢复动作。人类可读信息不应是唯一的机器可读契约。内部 Rust 错误变体可以按 crate 的兼容性策略演进。线级错误码除非有已记录的版本策略允许变更，否则应保持稳定。

### 5.5 错误传播与转换

**使用 `?` 进行直接传播：** 当当前函数能在不改变其语义含义的情况下传播错误时使用 `?` 操作符。

```rust
fn load_weights(
    path: &Path,
) -> Result<Weights, CheckpointError> {
    let bytes = std::fs::read(path)?;
    decode_weights(&bytes)
}
```

仅当 `CheckpointError` 有对 I/O 错误的刻意转换且 `decode_weights` 返回兼容结果时，这才有效。该示例不需要通用错误类型。

**在有意义的边界转换错误：** 当跨越抽象边界改变失败的含义或归属时转换错误。例如：

```text
std::io::Error
    -> checkpoint I/O error
    -> training-run failure
    -> CLI diagnostic and exit status
```

并非每个箭头都需要新包装。选择取决于契约与必须保留的诊断信息。转换不得静默丢弃诊断或恢复所需的信息。

**避免冗余包装：** 不要仅为添加重复文本而在每个函数调用处包装同一错误。

坏设计：

```text
operation failed
  caused by: operation failed
    caused by: operation failed
      caused by: operation failed
```

当附加上下文能识别有意义的操作、资源、阶段或边界时添加上下文。有用的上下文可能包括：加载特定的 checkpoint 组件；校验模型配置；写入特定的 checkpoint 代；在训练步骤中执行具名操作。敏感值、凭据、私有 prompt 内容与其他机密数据不得仅因可用就被加入错误上下文。

**在适当时保留源错误：** 来自标准库 I/O 或外部依赖的错误，在底层信息有用且可在内部安全暴露时，应保留其源。手动实现可以通过 `std::error::Error::source()` 暴露源。错误库（如 `thiserror`）在该依赖被允许且由工作区依赖策略证明合理时可以使用。本文档不强制特定错误库。

**避免在领域 API 中使用不必要的 `Box<dyn Error>`：** `Box<dyn std::error::Error>` 在有意聚合异构错误的应用边界可能合适。当调用方需要稳定变体或带类型恢复行为时，它不应替代核心领域 API 中有意义的 crate 局部错误。类型擦除的决策属于抽象契约，而不只是实现便利。

### 5.6 运行期 panic 策略

**不得基于 panic 处理运行期错误。** 生产运行期代码不得使用 `panic!()`、`unwrap()`、`expect()` 来处理可能因输入、I/O、资源限制、后端行为、并发、取消或其他运行期条件而失败的操作。该禁令包括以下位置的错误处理：张量操作；模型加载；分词；checkpoint 读写；训练循环；推理与生成；服务请求处理；工作线程与后台任务。改用显式错误传播。

**panic 不是校验的替代：** 不要依赖 panic 拒绝格式错误的外部数据。在假定有效性的操作之前校验维度、偏移、长度、配置值与其他受外部影响的数据。整数运算可能溢出时，使用带检查的算术或其他具有明确溢出行为的操作。分配可能失败时，在可用且与契约相关时使用适当的可失败分配 API。不要假定每种可能的分配或进程级内存不足失败都能被恢复。

**不变量与不可达路径：** 运行期禁令并不意味着每个逻辑上不可能的条件都应转换为任意错误。当不变量看似由构造保证时，实现应通过类型、可见性、所有权、校验或定义良好的内部契约使该保证显式。若一个被认为不可能的条件实际上能被输入、损坏数据、并发或后端触发，则它不是使用 `unwrap()` 或 `expect()` 的有效理由。仅当不变量真正是内部的、其破坏表示编程缺陷、且断言不用于处理预期运行期失败时，才可考虑显式不变量断言。此类情形需要评审，且不得绕过对外部数据的校验。首选方案是使无效状态不可表示，或在边界返回带类型错误。

**测试与示例：** 测试在失败应立即令测试失败时，可以使用 `unwrap()` 或 `expect()` 进行简明搭建与断言。但是：测试夹具应提供有用的失败信息；测试不得通过忽略 `Result` 值来隐藏错误；面向生产复用的示例应演示正确传播；仅测试的 panic 许可不得泄漏到生产代码。

**panic 恢复不是常规控制流：** panic 不等同于返回的错误。它可能使状态部分更新，可能阻止清理，或使周围代码的假设失效。顶层 panic 边界可能适合隔离 worker 或报告意外缺陷，但不得被视为带类型错误处理的通用替代。服务不得假定捕获 panic 就能使任意内部状态可安全复用。

### 5.7 外部输入与数据校验

所有不受信任或外部提供的数据必须在可能破坏内部不变量或触发不受控资源消耗之前被校验。来源包括：CLI 参数；HTTP 请求体；模型配置文件；tokenizer 词表与 merges；张量维度与偏移；checkpoint 元数据；序列化模型权重；数据集记录；插件或后端配置。

**在昂贵工作前校验：** 在可能时校验：整数范围与带检查算术；形状兼容性；文件大小与声明长度；支持的数据类型；必需字段；枚举与标识符值；格式版本；模型与 tokenizer 兼容性；最大序列长度；最大批大小；内存与工作预算。校验必须基于实际限制与契约。不要发明任意限制而不记录其目的与可配置性。

**将序列化数据视为不可信：** 声称包含特定形状张量的文件不得仅因头部如此声明就被信任。在基于其读取或分配之前，校验维度、元素数量、字节长度、偏移与支持的限制一致。在溢出可能使尺寸或偏移计算失效的任何地方，实现必须使用带检查的算术。格式错误的数据必须产生有意义的错误，而不是触发越界访问、不受控分配或基于 panic 的拒绝。

**不得泄漏内部实现细节：** 外部错误响应应传达失败类别与任何安全恢复动作。它们不应暴露：栈追踪；密钥或凭据；内部文件系统布局；私有 prompt 或训练数据；默认情况下的原始请求体；可能暴露敏感运维信息的后端实现细节。详细诊断属于适当受控的内部日志。

### 5.8 资源耗尽

资源耗尽是一等失败类别。潜在原因包括：过大的张量维度；大模型文件；超大 checkpoint 条目；长输入序列；大推理批次；无界队列；过多并发请求；训练期间的内存压力；过多临时存储使用。

**资源预算：** 可能消耗大量资源的操作应在显式预算下运行。取决于子系统，预算可能包括：最大字节数；最大张量元素数；最大序列长度；最大批大小；最大工作单元数；最大并发操作数；最大临时存储；最大执行时长。预算必须在适当边界强制。调用方提供的限制不得被允许绕过更严格的系统级安全限制。

**区分耗尽与无效输入：** 输入可能在结构上有效但超出运行限制。例如，张量形状在数学上有效但对配置的内存预算过大。当调用方需要不同恢复行为时，区分：无效形状；不支持操作；超出配置的资源限制；实际分配或后端资源失败。

**部分分配与清理：** 若操作在获取资源后失败，必须使系统处于已记录且安全的状态。优先使用 RAII 与基于所有权的清理。不得手动抑制清理失败，也不得在操作只完成一部分时返回成功。若多步操作可能部分修改持久状态，其提交与回滚语义必须被记录并测试。

### 5.9 取消与超时

取消与超时不同于普通操作失败，必须在异步与长时间运行操作中具有显式语义。

**取消：** 取消表示操作不再被需要或不再被允许继续。示例：客户端断开；调用方取消推理请求；训练运行被显式停止；worker 被要求关闭。若请求的工作未完成，取消不得被报告为成功完成。实现应在安全取消点停止工作并释放拥有的资源。若取消发生在修改持久状态的操作期间，结果状态必须遵循已记录的一致性策略。

**超时：** 超时表示操作超过了定义的时间预算。超时策略应指定：计时哪个阶段；超时是截止时间还是时长限制；是否包含排队时间；重试是否共享原始截止时间；进行中的工作会怎样；是否可返回部分输出。超时不得自动触发无界重试。

**保留区别：** 取消与超时可以由单独变体表示，或由带显式原因的共享类型表示，前提是调用方在必要时能区分它们。若服务或调用方需要不同行为，不要把二者都转换为通用内部错误。

### 5.10 重试策略

重试是策略决策，不是默认错误处理机制。

**仅在合理时重试：** 操作应仅在以下情况重试：1. 失败可能瞬态。2. 操作可安全重复，或其效果受幂等机制保护。3. 重试在已记录预算内。4. 重试尊重取消与截止时间。5. 重试不违反资源或并发限制。潜在瞬态失败示例包括临时网络错误或临时后端不可用。某个特定失败是否瞬态必须由实际子系统契约确定。无效输入、不支持操作、不兼容模型格式与确定性校验失败不应自动重试。

**有界重试：** 重试策略应指定：最大尝试次数；退避行为；最大经过时间；符合条件的失败类别；取消行为；可观测性要求。在分布式或争用系统中适当时可使用退避与抖动。重试预算必须契合操作的整体截止时间。

**避免重复副作用：** 训练与 checkpoint 操作需要特别注意。盲目重试部分完成的优化器更新或 checkpoint 写入可能产生重复效果或不一致状态。重试前判断操作：是否只读；是否幂等；是否有事务性提交边界；能否检测已完成的操作；是否需要回滚或恢复。若无法建立安全重试语义，返回失败并要求显式恢复，而不是猜测。

### 5.11 Checkpoint 与持久状态失败

Checkpoint 操作必须定义其在读取、写入、校验与恢复期间失败时的行为。Checkpoint 的具体格式契约见 design.md 的对应 crate 契约章节。

**读取失败：** checkpoint 读取在需要时必须区分有意义的失败类别，包括：文件未找到；权限拒绝；I/O 失败；不支持的格式版本；格式错误的元数据；不一致的长度或偏移；完整性校验失败；不兼容的模型配置；缺失所需参数数据。当公开契约不需要该区分时，这些类别可以合并，但安全恢复所需的诊断信息必须保留。

**写入失败：** checkpoint 写入应避免把部分写入的 checkpoint 作为成功提交的产物暴露。在存储系统与所选格式支持时，使用显式的暂存与提交策略，例如写入临时产物并仅在成功完成与校验后发布。实现必须记录其实际提供的保证。原子重命名、持久性与崩溃一致性依赖文件系统与平台行为，不得被普遍假定。

**恢复：** 恢复逻辑必须区分已验证有效的 checkpoint 与部分写入或损坏的产物。除非显式要求并清晰报告，实现不得静默地用空模型、默认权重或另一个 checkpoint 替换损坏状态。任何可能丢弃用户数据或训练进度的恢复动作都需要刻意的策略与适当的测试。

### 5.12 数值与后端错误

数值计算需要显式处理无效值与后端失败。示例包括：不支持的 dtype 或操作；形状不匹配；契约禁止时出现的非有限值；无效的归约维度；后端初始化失败；设备内存耗尽；内核执行失败；不支持的硬件能力。

**不要把数值结果与错误混为一谈：** NaN 或无穷并非在每个操作中都是错误。其含义取决于操作与契约。除非操作明确指定该行为，内核不得静默地把意外非有限值替换为零或其他默认值。若操作要求有限值，校验必须使该要求显式。

**后端特定诊断：** CPU 后端与任何未来加速器后端可以使用后端特定的内部错误。公开抽象应只暴露调用方所需的区分，例如不支持操作、资源耗尽或执行失败。不要迫使高层模型或推理代码依赖特定后端的内部错误表示。

**部分计算后不得伪造成功：** 失败的内核或不完整操作不得返回正常结果，除非 API 明确定义了有效的部分结果契约。若支持部分结果，其完整性与有效性必须被显式表示。

### 5.13 训练与推理中的错误处理

训练契约与推理运行契约见 design.md 的对应 crate 契约章节。

**训练：** 训练失败可能发生在大量工作完成之后。训练层在相关时应区分：无效训练配置；数据集或批加载失败；前向传播失败；反向传播失败；优化器更新失败；checkpoint 持久化失败；取消；资源耗尽。失败的训练步骤不得被报告为成功步骤。若错误发生在改变状态的更新期间，实现必须定义更新是原子的、可恢复的还是可能部分的。不要假定每个失败都能回滚。记录并测试实际实现的保证。

**推理：** 推理失败在区分影响调用方时，应区分请求校验、模型就绪、不支持功能、资源限制、取消、超时与后端执行失败。推理请求不得仅为记录请求级错误或临时状态而修改共享模型权重。请求特定上下文、取消状态、生成限制与诊断应保持限定在请求或执行上下文内。

**流式输出：** 流式接口必须记录在已输出内容之后发生错误时的行为。流不得以暗示成功完成的方式静默终止，而实际操作已失败。若协议支持终止错误事件，一致地使用它们。若传输无法表达终止错误，该限制必须被记录，并可通过相关运维通道观察。

### 5.14 CLI 与服务错误映射

内部错误与外部呈现有不同要求。

**CLI：** CLI 应：打印简明、可操作的诊断；命令失败时使用非零退出状态；在有用时保留详细源上下文；默认避免倾倒栈追踪；避免暴露密钥或敏感输入；在适当处区分用法错误与运维失败。除非命令的已记录契约明确如此定义，CLI 不得打印错误后以成功退出。

**HTTP 与服务 API：** 服务应在服务边界把内部错误映射为协议级响应。映射必须基于错误语义，而不是字符串匹配。当客户端需要机器可读区分时，响应应包含稳定的错误码。响应不得暴露原始内部错误链、文件系统路径、栈追踪、凭据或私有模型输入。服务不得仅因响应本身被成功构造就声称操作成功。

**将传输依赖保持在边界：** 核心 crate 不得依赖 HTTP 状态码或 CLI 退出码。协议特定映射属于 serve、cli 或其他明确指定的应用边界。

### 5.15 日志、指标与诊断

错误应可观测，同时不制造过多噪声或暴露机密数据。

**在适当层记录日志：** 拥有足够上下文并拥有恢复决策的层通常应负责记录失败。避免在每个函数边界记录同一传播错误。重复日志使单次失败看起来像许多独立事件，并掩盖有用诊断。

**保留因果信息：** 诊断应包含有用的操作上下文，例如：操作或阶段名；相关非敏感标识符；错误类别；操作是否被重试；恢复是否成功；失败是预期还是意外。避免仅为改进调试而记录整个张量、完整模型权重、原始请求体、私有 prompt、凭据或任意用户数据。

**指标：** 在存在运维指标的地方，错误类别应适合聚合。指标标签必须有界基数。任意错误信息、完整路径、请求 ID 与用户控制的字符串不应被用作指标标签。指标应区分需要不同运维响应的失败，例如资源耗尽与无效输入。

**不要重复报告：** 底层函数通常应返回错误，而不是既把它记录为最终失败又返回给调用方再次记录。当下层事件独立地具有运维意义时，在传播前记录日志可能合适，该决策应是显式的。

### 5.16 错误测试要求

错误行为是 API 契约的一部分，必须被测试。测试量应随操作的风险与复杂度成比例。

**必需测试类别（在适用时）：** 有效输入；无效输入；边界值；整数溢出；缺失文件或资源；格式错误的序列化数据；不支持的版本或操作；资源限制违反；后端失败；取消与超时；部分失败与清理；重试限制；持久状态一致性；错误转换与公开映射。并非每个类别适用于每个函数。测试选择必须反映实际失败模式。

**断言语义而非措辞：** 优先检查错误变体或稳定码：

```rust
assert!(matches!(
    result,
    Err(ShapeError::DimensionOverflow)
));
```

当确切文本本身就是已记录的用户面向契约时，测试可以断言显示文本。否则应避免精确措辞断言，因为它们使无害的诊断改进变得不必要地昂贵。

**测试资源与清理行为：** 对于分配内存、创建文件、改变状态或派生任务的操作，失败测试应验证资源被释放且状态与已记录契约保持一致。

**不要只测试快乐路径：** 对有效输入返回正确值但对格式错误输入 panic 的函数不满足错误处理契约。在失败是预期且可恢复的地方，测试应演示显式错误传播，而非基于 panic 的行为。

### 5.17 公开 API 与兼容性

公开错误类型是 API 表面的一部分。在改变公开错误类型之前，评审者应评估：下游调用方是否匹配其变体；新变体是否影响穷尽匹配；错误码是否被外部记录；错误源是否仍可访问；转换行为是否改变；变更是否改变重试或恢复语义。

**避免泄漏实现细节：** 公开错误应暴露领域相关含义，而不是每个内部辅助函数或后端实现细节。后端替换不应迫使无关调用方重写其错误处理，除非公开契约有意改变。

**错误信息与兼容性：** 人类可读信息应有用且清晰，但除非显式记录，不应被视为稳定标识符。当外部客户端需要稳定性时，定义专门的错误码或协议级错误结构。

**不得进行误导性错误转换：** 错误转换必须保留原始失败的含义。不得把无效输入无理由地转换为内部服务器错误；不得把资源耗尽转换为无效输入；不得把取消转换为成功；不得把损坏的持久状态转换为普通缺失值结果；不得把不支持功能转换为无关后端失败。转换可以简化细节，但必须保留接收层所需的语义区分。

### 5.18 错误处理的依赖策略

工作区可以在某错误处理库提供明确收益时采用它。不得仅因流行或能消除少量样板而引入依赖。评审者应考虑：核心 crate 是否需要该库；它是否引入不想要的依赖耦合；它是否影响编译时间或二进制大小；其公开类型是否会跨 crate 边界泄漏；标准 Rust trait 与显式枚举是否足够。用于人体工学错误定义的库不会消除正确设计错误语义的要求。工作区应避免在 crate 间混合不兼容的错误约定，除非有已记录的理由。

### 5.19 反模式

当以下模式掩盖有意义的失败或违反 crate 边界时，必须拒绝。

**静默抑制错误：**

```rust
let _ = save_checkpoint(path);
```

当 checkpoint 持久化是成功完成的必需条件时，这不可接受。忽略结果仅在失败对契约有意无关且该决策显式时方有效。必需的持久化、状态更新与安全检查不符合条件。

**把每个失败转换为 None：**

```rust
let model = load_model(path).ok();
```

这抹去了缺失与失败之间的区别。

**基于字符串的重试决策：**

```rust
if error.to_string().contains("temporary") {
    retry();
}
```

这创建了不稳定、未记录的控制流契约。

**宽泛回退行为：**

```rust
let output = run_model(input).unwrap_or_default();
```

这可能使失败的模型执行看似成功。

**对不受信任数据 panic：**

```rust
let dimension = parsed_dimension.unwrap();
```

这把格式错误或缺失的外部数据变成进程级失败。

**处处使用通用错误类型：**

```rust
type Result<T> = std::result::Result<T, Box<dyn std::error::Error>>;
```

这样的类型在刻意的应用边界可能合适，但不应替代工作区内所有领域特定错误。

**在每一层重复记录日志：** 记录每次传播步骤会产生重复诊断，使因果分析更难。

**无界重试：** 无限重试可能放大故障、耗尽资源或忽略取消。

**暗示恢复但未执行的错误：** 除非实现实际确立了该保证，错误信息不得声称状态已恢复、回滚或保留。

## 6. 命名标准

### 6.1 规范动词表

规范动词表固定了全局动词集，使同一操作始终以同一方式表达。资源释放不是动词：它由作用域与 `Drop` 拥有（OW1、NM3），因此不存在释放动词。

| 动词 | 含义 | Rust 机制 |
| --- | --- | --- |
| `get` | 读取值而不转移所有权 | `fn get<field>(&self) -> T` |
| `set` | 覆盖已存储的值 | `fn set<field>(&mut self, ...)` |
| `new` | 类型的主构造函数（等价于 init） | `fn new(...) -> Self` |
| `from` | 从显式来源构造 | `fn from<source>(source) -> Self` |
| `parse` | 校验并解码不可信输入 | `fn parse(bytes) -> Result<Self, E>` |
| `load` | 恢复持久状态 | `fn load<thing>(...) -> Result<T, E>` |
| `store` | 持久化状态 | `fn store<thing>(...) -> Result<(), E>` |
| `read` | 从外部来源读取而不解码 | `fn read<thing>(...)` |
| `write` | 写入外部 sink | `fn write<thing>(...)` |
| `open` | 获取句柄 | `fn open(...) -> Result<Handle, E>` |
| `close` | 显式释放句柄 | `fn close(...)` |

`new` 只命名返回 `Self` 的构造函数。返回不同类型的可失败工厂不得命名为 `new`：Clippy 的 `new_ret_no_self` 会拒绝它，且该名称会误导读者对构造内容的认知。用 `new<object>` 形式命名所产出的值，如 `architecture::newmodel`，或在来源是名称显著部分时使用 `from<source>`。

除固定表外，工作区使用以下额外动词，它们不是表内动词的同义词，因此不违反 NM3：`check`（校验前置条件并返回 `Result`）、`apply`（驱动已存储的操作）、`dispatch`（选择操作）、`run`、`reset`、`clear`、`add`、`insert`、`append`、`bind`、`collect`、`cancel`、`try`（可失败 `try_reserve`/`try_admit` 风格）、`encode`/`decode`、`format`/`render`、`record`、`sample`、`step`、`restore`/`save`、`generate`、`prefill`，以及镜像数学的算子名（`matmul`、`softmax`、`relu`、`silu`、`gelutanh`、`rmsnorm`、`rope`、`embedding`、`attention`）。这些在此登记以使集合封闭可评审；添加新的非表内动词需要在本节添加一行。

### 6.2 禁用同义词

NM3 禁止混用同义词。以下动词不得作为函数或方法名的起始 token，因为每个都与某个规范动词重复。强制门机械地执行该列表。

| 禁用 | 规范 | 原因 |
| --- | --- | --- |
| `build`, `create`, `make`, `construct`, `instantiate`, `assemble` | `new` / `from` | 构造函数是 `new`；从来源构造是 `from<source>` |
| `fetch`, `retrieve`, `obtain`, `acquire`, `query` | `get` | 读取值是 `get` |
| `assign`, `put` | `set` | 覆盖值是 `set` |
| `dispose`, `free`, `release`, `dealloc` | 作用域 / `Drop` | 释放不是动词（OW1、NM3） |

`parse` 是规范的，不是 `read` 的同义词：`read` 从来源移动字节，`parse` 校验并将其解码为带类型的值。同时做两者的函数必须命名为 `parse<thing>`，且必须在文档中写明其来源。

**为何使用同义词拒绝列表而非完整允许列表：** 工作区有 518 个不同的生产函数名。其中绝大多数要么是标准库强加给实现的 trait 方法（`fmt`、`deref`、`drop`、`eq`、`default`、`next`、`iter`、`from`），要么是镜像数学的算子/领域名词（`matmul`、`softmax`、`rmsnorm`、`rope`）。若门要求每个名称都以表内动词开头，则会拒绝这些名称，或需要一个列出数百条目的豁免文件，从而把检查变成橡皮图章、失去意义。拒绝列表改为把实际的 NM3 要求——不混用同义词——编码为一个小而封闭、可评审的集合。以被禁用同义词开头的名称是真实缺陷；以任何其他 token 开头的名称交由人工评审 NM1 自描述性。这使机械门保持锐利且低噪声。被否决的替代方案见本章"备选方案"。

### 6.3 缩写

NM1 要求自描述名称并禁止没有共同约定的缩写。短名称仅当位于以下白名单中，或限定为局部临时变量（NM4）时才可接受。

已批准的缩写：`id`、`eps`、`lr`、`dim`、`seq`、`max`、`min`、`fan`、`cos`、`sin`、`std`、`lo`、`hi`、`n`（元素数）。

拒绝：任何其他领域词的缩写。当标识符比单个表达式更宽时，写 `tokenizer` 与 `vocabulary`，而非 `tok` 与 `vocab`。NM4 允许函数体内使用单字母临时变量（`i`、`j`、`k`、`t`、`tmp`）。

### 6.4 命名梯度

作用域越广，名称越完整。公开跨 crate 符号完整拼出其对象（`getkeyvalueheads`）；模块私有辅助可以更简（`reshape`）；循环临时变量最小（`i`）。这是 SHOULD，不是缺陷，也不机械强制。

### 6.5 常量、宏与类型别名

常量与宏必须使用大写紧凑拼写（NM5）：`[A-Z][A-Z0-9_]*`。

类型别名不得隐藏所有权或可变性。`type buffer = Vec<f32>` 可接受；读起来像拥有值却别名一个引用的名称，或隐藏 `mut` 的名称，不可接受。类型、trait、enum 与变体标识符按根 Cargo.toml 声明的无分隔符小写约定（M4、A8）；本文档不改变该放宽。

### 6.6 豁免纪律

任何沉默命名 lint（`non_snake_case`、`non_camel_case_types`、`non_upper_case_globals`）的 `#[allow(...)]` 必须带有注释，写明其所依赖的 clause 与理由。没有 clause 引用的命名豁免是缺陷。根 Cargo.toml 中的工作区级放宽已在声明处记录其 M4 声明；源码级豁免必须同样如此。

### 6.7 强制门

`scripts/checknaming.sh` 是机械门。它对 `crates/*/src` 并排除 `#[cfg(test)]` 区域断言：

1. 没有函数或方法名以被禁用同义词开头。
2. 每个 `const` 名匹配 `[A-Z][A-Z0-9_]*`。
3. 每个 `macro_rules!` 名匹配 `[A-Z][A-Z0-9_]*`。
4. 每个命名 lint 的 `#[allow(...)]` 都写明 NM clause。

该门接入 `scripts/check.sh`，位于 Clippy 之后、rustdoc 之前。非零退出使检查失败。排除测试区域，因为 NM4 允许简短局部名称，且测试辅助不属于任何契约。

### 6.8 结论记录

改变本标准、拒绝列表或门的变更必须用已执行的命令及其退出码更新 conformance 记录中对应行。

### 6.9 备选方案

- **每个函数名的完整允许列表。** 否决：它将重述 518 个名称（多数为 trait 方法或算子名词），并把新名称橡皮图章化而非评审。拒绝列表针对实际的 NM3 缺陷面。
- **仅通过 Clippy 强制动词表。** 否决：Clippy 没有同义词知识，无法知道 `build` 与 `new` 重复。该规则是项目特定的，属于项目自己的门。
- **重命名使用简短名称的测试辅助（`ds`、`ckpt`、`caps`）。** 否决：NM4 明确允许最小局部名称，且测试辅助在所有公开契约之外。重命名它们是未证实缺陷的改动。

## 7. 公开 API 设计与演进

### 7.1 API 类别

每个公开接口应有一个可识别的稳定性类别。

**内部实现接口：** 仅在一个 crate 内使用的接口应保持私有或 `pub(crate)`。示例：内部辅助函数；临时计算结构；私有内核实现细节；内部缓存机制；不属于跨 crate 契约的中间表示。当实现需求变化时，这些接口应可自由更改。

**工作区接口：** 主要暴露给本仓库内其他 crate 的接口。示例：供 CPU 内核消费的张量原语；供 autograd 消费的算子契约；供推理消费的模型构建接口；供训练与推理消费的 checkpoint 抽象。工作区接口应尽可能窄。工作区 crate 之间的依赖并不自动证明一个稳定、外部支持的 API 合理。当接口需要跨 crate 边界时，优先暴露满足实际消费者的最小类型、trait 与方法集合。

**外部公开接口：** 有意为工作区之外的消费者支持的接口。在把接口视为外部稳定之前，维护者必须确定：包含 crate 是否面向外部消费；接口是否受兼容性保证覆盖；适用哪个发布与版本策略；破坏性变更将如何沟通；接口是否有足够测试与文档。除非项目明确采用了相应承诺，不得声称接口稳定、semver 兼容或生产支持。

**实验接口：** 当实验必要时可以暴露实验接口，但其状态与局限必须清晰。实验状态不得作为良好设计、错误处理或测试的替代。在实验接口成为稳定之前，评审其命名、类型约束、所有权语义、错误行为、兼容性影响与实际消费者需求。

### 7.2 可见性与公开面

**默认私有：** Rust 可见性必须遵循最小暴露原则。按顺序优先：1. 私有项。2. `pub(super)`，当父模块边界足够时。3. `pub(crate)`，用于 crate 级实现需要。4. 受限可见性如 `pub(in path)`，在适当时。5. `pub`，仅当真实消费者需要访问时。

开发者不得仅为使测试方便而暴露内部类型或添加公开项。每个测试都在仓库根通过 crate 的公开接口触达；仅测试的 hook 是契约缺陷，而不是放宽可见性的理由（见本文《测试策略与质量门》章节的黑盒契约优先测试决策）。

**显式公开导出：** 每个 crate 应使其预期公开接口易于发现。crate 可以使用少量公开 facade 模块或根级 re-export 来呈现连贯接口。re-export 必须有意识，因为它们会创建额外兼容承诺。不要 re-export 每个内部模块、依赖类型或实现辅助。

例如，crate 可以暴露：

```rust
pub use tensor::Tensor;
pub use tensor::TensorError;
```

仅当这些类型真正属于其预期公开契约时。该示例说明 API 设计模式；它不声称这些导出已存在于工作区。

**避免意外公开 API：** 在合并引入 `pub` 的变更之前，评审新可见性是否必要。以下本身不是充分理由：实现用宽可见性写起来更容易；未来消费者可能需要该项；某个依赖当前使该类型可访问；测试能更方便地访问该项；公开接口因附加方法看似更完整。优先支持已验证用例的最小接口。

**公开字段：** 公开字段暴露表示并限制未来实现变更。当不变量或未来表示变更重要时，公开 struct 应优先使用私有字段加显式构造函数与访问器。公开字段在以下情况可能合适：字段是独立数据；其不变量平凡；直接构造与变更是预期行为；暴露表示不会造成不合理兼容负担。不要仅为对称而添加 setter。每个方法应表达真实操作或支持的用例。

### 7.3 API 设计原则

**围绕真实能力设计：** 接口应表示有意义的能力或领域概念。好的接口使以下清晰：可用什么操作；哪些输入有效；改变什么状态；转移或借用什么所有权；可能有哪些失败；消费者可依赖哪些行为。避免不阅读实现就无法理解其目的的 API。

**最小化概念复杂度：** 少量显式、可组合的接口优于大型泛型抽象框架。不要仅为一消除少量重复代码而引入抽象。创建新公开抽象前，回答：哪些真实实现或消费者需要它？它标准化了什么行为？它强制了什么正确性约束？同一需求能否由私有辅助或现有接口满足？它将引入哪些未来兼容义务？若收益是投机性的，保持抽象私有，直到出现具体需求。

**避免字符串类型化 API：** 当类型能表达预期契约时，不要把结构化选择、操作模式或领域状态表示为任意字符串。对于有限、有意义的替代项，优先使用枚举或专门类型。

例如：

```rust
pub enum DeviceKind {
    Cpu,
}
```

当 API 只支持固定设备类型集时，它优于接受任意字符串如 `"cpu"`。除非抽象有具体目的，不要仅为使 API 看似更强类型而创建单变体枚举。字符串对真正自由形式的值（如文件路径、标签或用户提供文本）仍合适。

**避免隐藏全局行为：** 公开 API 不应依赖未记录的全局可变状态、隐式环境配置或不可见请求特定状态。实质影响行为的依赖与配置应在函数参数、构造选项或清晰记录的环境接口中显式。调用方应能从签名与文档理解操作的重要输入。

### 7.4 Trait 设计

trait 是 Rust 中重要的组合边界，也是可能变得昂贵修改的长期契约。

**围绕内聚能力定义 trait：** trait 应描述一个连贯能力。避免组合无关职责的大型 trait，例如：张量存储与神经网络优化；模型加载与 HTTP 请求处理；checkpoint 序列化与训练循环调度；数值计算与日志基础设施。当职责有不同消费者、生命周期、失败模式或实现要求时分离它们。但是，不要把每个方法拆成单独 trait。过度碎片化会使普通操作更难发现与组合。正确的边界是有真实理由独立存在的最小连贯能力。

**优先静态分发：** 静态分发应是核心计算与性能敏感路径的默认。泛型参数与具体类型允许编译器解析实现而无需动态分发。仅当运行期多态提供已证实的收益时才使用 `dyn Trait`，例如：运行期选择的实现集合；插件式扩展点；同一接口后的异构对象；减少泛型类型传播的实质需要。不要仅因存在 trait 就引入动态分发。反之，当运行期选择是实际需求时，不要禁止动态分发。选择必须遵循用例，而非无条件偏好某一机制。

**避免投机式 trait 层级：** 没有明确需要时，不要创建多层 marker trait、supertrait、关联 trait 或 blanket 实现。每个 trait 层应传达有意义的能力、约束或契约。必须谨慎评审 blanket 实现，因为它们可能：阻止下游添加实现；引入方法解析歧义；增加 trait bound 复杂度；与未来实现产生意外交互。避免仅用于省去微不足道转发代码的 blanket 实现。

**有意使用关联类型：** 当实现自然为某能力确定一个类型时，关联类型合适。当调用方需要独立选择或变化该类型时，泛型类型参数更合适。选择为实际消费者产生最清晰契约的模型。不要仅为最大化理论灵活性而添加关联类型或泛型参数。

**保持 trait 方法连贯：** 每个必需的 trait 方法必须有清晰的语义契约。trait 应定义：前置条件；输入输出语义；错误行为；状态与变更保证；相关数值保证；线程安全要求（如有）；重复调用是否预期确定性。当默认行为对每个符合实现都正确时可以提供默认方法。不要提供静默削弱正确性或性能保证的默认实现。

**避免不必要的 trait bound：** 仅当契约需要时才添加 `Send`、`Sync`、`'static`、`Clone` 或其他 bound。不必要的 bound 会阻止有效实现被使用，并把实现细节传播到无关 API。尤其：`Send` 与 `Sync` 应反映真实的跨线程需求；`'static` 不得仅为简化局部编译器错误而添加；当借用、所有权转移或不同显式操作足够时不得要求 `Clone`；为异步执行引入的 bound 必须由实际执行模型证明合理。

**对象安全：** 当动态分发是支持的需求时，验证 trait 可作为 trait object 使用且其方法签名兼容该需求。当没有动态消费者时，不要仅为使接口对象安全而扭曲原本合适的静态分发接口。若静态与动态用例都需要，考虑刻意设计分离，而不是在没有消费者时添加复杂度。

### 7.5 函数签名与类型设计

**使所有权显式：** 函数签名应传达所有权与借用要求。使用：`&T` 用于只读借用；`&mut T` 用于独占可变借用；拥有型 `T` 当被调用方需要所有权、可能保留该值或应消费它时；`Cow<'a, T>` 或类似抽象仅当避免有意义分配或所有权转移能证明额外复杂度合理时。

不要仅为简化签名而克隆大型张量、参数数组、模型数据或其他昂贵值。不要引入复杂生命周期关系，除非它们表达输入与输出数据之间的真实关系。

**返回值应表达结果：** 函数应返回传达操作结果的最小有用结果。优先显式返回类型，而非：改变隐藏状态来传递结果；返回变得难以解释的松散结构化元组；在领域类型提供有意义不变量时返回不透明集合；使用哨兵值表示失败。对于有多个语义不同字段的结果，当命名 struct 能提升清晰度与可维护性时优先使用它。

**避免过长参数列表：** 当若干参数表示一个连贯概念时，考虑配置或选项类型。不要为每个函数创建 builder。builder 引入更多 API 表面，并可能使校验与错误处理复杂化。当构造有很多可选设置、分阶段配置或有意义校验要求时 builder 合适。当 builder 不带来有意义价值时，带少量清晰参数的简单函数更可取。

**在类型中编码不变量：** 类型应使无效状态难以表示。示例：为不同坐标系或单位使用不同 distinct 类型；为有限状态使用枚举；为受约束值使用已验证配置类型；为不得混用的标识符使用 newtype；当操作顺序重要时使用显式状态转换。类型级建模必须与问题成比例。当直接运行期检查更清晰且同样可靠时，不要引入精巧类型机制。

**避免泄漏实现细节：** 公开签名不应暴露内部数据结构、临时计算缓冲、缓存布局或第三方类型，除非这些细节是契约的有意部分。内部表示的变更不应要求公开 API 变更，除非底层语义真正改变。

### 7.6 错误契约

**使用显式错误传播：** 可失败的公开操作必须通过适当的 `Result<T, E>` 返回类型暴露其失败行为。错误语义、对 `panic!`/`unwrap()`/`expect()` 的运行期禁令与断言策略由本文《错误处理与失败语义》章节定义；本节只陈述公开签名义务。

**设计有意义的错误类型：** 公开错误类型应帮助调用方理解并响应失败。错误契约应区分实质不同的失败类别，例如：无效参数或配置；不支持操作；形状或维度不兼容；数值失败；I/O 失败；序列化或反序列化失败；资源耗尽（在可靠可检测时）；内部不变量破坏。不要在没有明确收益时为每个辅助函数创建唯一的公开错误类型。当错误属于同一连贯抽象时使用共享错误类型。当消费者需要区分失败类别或领域需要清晰边界时使用专门类型。

**保留有用上下文：** 传播底层错误时，保留足够上下文以识别失败操作与相关领域对象。避免把每个失败转换为通用字符串，如果那会破坏调用方用于恢复、诊断或测试的信息。错误信息应对开发者可理解，且不得被视为唯一稳定的机器可读契约。

**不要暴露不稳定的错误实现细节：** 消费者应匹配已记录的错误类别，而不是解析任意人类可读信息。若调用方需要稳定分类，暴露枚举变体、错误 kind 或其他结构化表示。错误类型是公开 API 的一部分，必须像普通数据类型一样为兼容性而评审。

### 7.7 数值与计算契约

因为本工作区包含数值与机器学习计算，API 必须记录实质影响正确性的行为。在适用时指定：张量形状与布局要求；dtype 与支持的数值格式；设备或执行后端要求；广播与归约语义；输出形状与 dtype；累加精度；数值容差预期；空输入与边界维度的行为；NaN、无穷、溢出与下溢的处理；确定性保证与局限；是否允许变更；操作是分配新存储还是可能复用现有存储。

除非项目已明确建立并测试该保证，不要承诺跨不同后端、硬件、编译器配置或执行模式的按位相等。公开 API 不得暗示强于其实现能支持的数值保证。性能声明必须由可复现测量支撑。文档不得在没有适当基准证据时断言 API 或实现更快。

### 7.8 状态、可变性与并发

**使状态转换可见：** 修改状态的操作应通过签名与文档传达该事实。避免看似只读却修改外部可观察状态的 API。记录重复调用是否：产生独立输出；改变接收者；消费接收者；依赖先前调用；需要独占访问。

**分离模型状态与请求状态：** 模型权重与可复用模型结构不得包含请求特定可变状态。每请求输入、临时激活、推理缓存、解码状态、取消状态与类似可变数据必须有适合该操作的显式生命周期。可复用模型对象应在其已记录的并发契约下可安全共享。若特定实现需要独占访问，该限制必须在其类型或 API 文档中显式。不要仅为使类型看似线程安全而添加 `Mutex`、`RwLock` 或原子状态。同步必须遵循真实并发需求与已定义的所有权模型。

**记录线程安全保证：** 实现 `Send` 或 `Sync` 是有意义的 API 属性。不要在没有分析底层数据与不变量的情况下，为满足假定需求而添加显式 trait 实现、unsafe 实现或同步机制。本项目禁止 unsafe；所有 API 与实现设计必须保持在该约束内。

### 7.9 配置与特性开关

**优先显式配置：** 实质影响行为的配置应在构造时或操作边界可见。避免使行为依赖未记录环境条件的隐藏默认值。当默认值影响正确性、数值行为、资源使用或性能时，必须记录它们。

**保持配置内聚：** 配置类型应分组共享生命周期与目的的相关选项。避免混合张量执行、训练、checkpoint 存储、网络与命令行呈现等无关关注点的单一全局配置对象。按职责分离配置，让高层组件组合相关部分。

**特性开关：** 当提供真实收益时，特性开关可用于可选能力、平台支持或依赖选择。不应仅为制造模块化表象而引入。对每个公开特性开关，记录：它启用的能力；任何额外依赖；相关平台限制；与其他特性的交互；它是否改变公开 API 可用性；已测试的支持组合。避免创建未记录或不可测试的公开 API 状态的特性组合。特性门控接口必须在发布前在相关特性配置下检查。

### 7.10 依赖与公开类型泄漏

公开 API 应最小化对外部 crate 类型的不必要依赖。在公开签名中暴露第三方类型会使消费者耦合到该依赖的 API 与版本决策。

在暴露此类类型之前，确定是否：1. 外部类型是自然的领域表示。2. 消费者需要外部类型的完整功能。3. 一个小的项目自有类型会提供更清晰契约。4. 包装该类型会增加不必要转换或维护成本。

不要自动包装每个外部类型。当包装建立领域含义、校验不变量、隔离依赖演进或收窄过宽接口时，它才是合理的。依赖升级必须包含对受影响公开签名与行为契约的评审。

### 7.11 文档要求

**公开项文档：** 公开类型、trait、函数与方法必须有适合其复杂度与目标读者的文档。文档应解释：该项做什么；何时应使用；前置条件与约束；所有权与变更行为；错误与失败条件；数值或确定性保证；相关示例。文档必须描述可观察行为，而不仅是重述项的名称或签名。

**示例与 doctest：** 公开 API 应为非平凡用例包含简明示例。示例在可行时必须编译，且必须反映预期的支持用法模式。优先演示跨相关接口边界的组合，而非隐藏关键搭建的孤立片段。当示例依赖可选特性时，其特性要求必须清晰。

**避免不支持的承诺：** 文档不得声称：未作为策略采用的兼容性；未建立的线程安全；未验证的确定性；实现无法保证的数值精度；没有基准证据的性能改进；未验证后端或格式的支持。若行为是实现相关、实验性的或尚未保证的，明确陈述该限制。

### 7.12 兼容性与 API 演进

**显式定义兼容性策略：** 在承诺兼容性之前，项目必须区分内部工作区接口与外部支持的 API。若 crate 已发布并遵循 Semantic Versioning，其公开 API 的变更必须按 crate 采用的版本策略分类。不要假定每个工作区 crate 都已发布，或每个公开项都外部稳定。

**潜在破坏性变更：** 以下变更可能破坏源码兼容性或改变行为：移除或重命名公开项；改变公开函数的参数或返回类型；向公开 trait 添加必需方法；改变 trait bound；改变所有权或借用要求；添加或移除 `Send` 或 `Sync` 等 auto-trait 行为；改变公开字段的可见性或类型；改变已记录的数值、错误或确定性保证；以改变可观察行为的方式改变默认值；改变公开项的特性要求；收窄有效输入或支持用例集合。每个变更的影响必须在实际兼容性契约的上下文中评估。

**增量变更并非总是无害：** 添加公开项通常比移除破坏性小，但添加仍可能产生兼容问题。示例：添加必需 trait 方法；当下游允许穷尽匹配时添加新枚举变体；引入与消费者实现冲突的 blanket 实现；向现有泛型 API 添加 trait bound；添加与消费者常定义方法冲突的方法；添加改变可用 API 的特性要求。兼容性评审必须考虑下游实现与用法模式，而不仅是现有源文件是否仍能编译。

**有意使用 `#[non_exhaustive]`：** 当公开 struct 或 enum 被有意设计为可演进而不要求下游穷尽构造或匹配时，`#[non_exhaustive]` 可能合适。它不应自动添加到每个公开类型。使用前考虑：外部消费者是否需要直接构造该类型；穷尽匹配是否属于预期 API；未来添加是否真正可能且有意义；施加给调用方的人体工学成本；类型的稳定性类别是否证明该限制合理。该属性本身影响下游使用，必须被视为有意的 API 决策。

**弃用：** 当外部支持的 API 需要替换时，弃用应在可行时提供迁移路径。弃用通知应识别：被弃用项；推荐替代项；任何语义差异；预期迁移方式；相关移除或兼容性策略（若已采用）。当继续支持可行时，不要没有有意义理由或替代策略就弃用 API。

**迁移策略：** 对于重大 API 变更，在适当时提供迁移示例或发布说明。优先允许消费者增量过渡的变更，当这样做不会保留错误行为或施加不成比例复杂度时。不要在没有已记录维护理由的情况下无限期维护冗余兼容层。

### 7.13 API 测试

公开 API 正确性必须通过测试其已记录契约来验证。

**契约测试：** 测试应覆盖：有效输入与预期输出；无效输入与错误类别；边界值；所有权与变更预期（在可观察时）；数值语义与容差；确定性保证（如适用）；支持的配置与特性组合；重要并发保证（如适用）。当目的是验证公开契约时，测试不得仅依赖私有实现细节。

**外部消费者视角：** 对于面向外部使用的接口，包含以消费者会遇到的方式行使 API 的测试或示例。此类验证应检测对私有可见性、未记录导入或仅实现辅助函数的意外依赖。在可行时编译文档示例并测试相关公开特性配置。

**兼容性验证：** 在承诺 API 兼容性的发布之前，对照项目采用的兼容性策略验证预期公开面。适当时可以使用自动 API 比较，但工具必须被配置为反映实际稳定性保证。自动差异是评审证据，而不是理解语义与行为变更的替代。

**避免仅测试的公开扩张：** 不要仅为支持测试而使生产接口公开。优先模块级单元测试、针对支持接口的集成测试或窄范围测试基础设施。可测试性重要，但它不自动证明扩张公开契约合理。

### 7.14 API 变更工作流

每个有意义的公开 API 变更必须遵循刻意的评审流程。

**步骤 1 识别消费者：** 确定哪些现有或计划中的消费者需要该变更。记录消费者是：crate 内部；另一工作区 crate；外部消费者；仅测试或基准。若没有具体消费者，重新考虑是否现在就该暴露该 API。

**步骤 2 评审所有权与依赖边界：** 检查拥有 crate 的职责与依赖方向。确认变更不引入循环依赖，也不使低层 crate 依赖高层子系统。不要仅为使公开签名方便就在 crate 间移动类型而不考虑架构归属。

**步骤 3 定义契约：** 指定：输入与前置条件；输出与后置条件；错误行为；所有权与变更；数值语义（如适用）；性能预期（如适用）；稳定性类别；兼容性影响。

**步骤 4 比较替代方案：** 考虑需求能否由以下满足：私有辅助；更窄可见性层级；现有 trait 或类型；对现有接口的小扩展；新公开类型或 trait。选择满足真实需求的最不复杂选项。

**步骤 5 实施最小连贯变更：** 避免把无关 API 重新设计与实现工作合并。保持每个变更足够聚焦以便独立评审、测试与回退。

**步骤 6 验证接口：** 运行相关单元测试、集成测试、文档测试、特性检查与兼容性检查。新算子或计算 API 还必须满足项目的算子测试与基准要求，包括边界测试、数值测试与至少一个性能基准。

**步骤 7 评审最终差异：** 检查所有可见性变更、re-export、trait bound、错误类型、特性声明、文档与生成的 API 表面。验证没有内部细节意外变为公开。

**步骤 8 记录兼容性决策：** 对于外部支持的 API，在适当的项目文档或发布说明中记录任何破坏性变更、弃用、迁移要求或稳定性策略决策。若未运行相关检查，不要声称兼容性已验证。

### 7.15 AI 辅助 API 开发

AI 辅助变更必须遵循与人类编写变更相同的工程要求。AI 工具不得：仅为解决编译器错误而使项公开而不评审架构边界；在没有具体用例时发明 trait 或泛型抽象；在没有已证实需求时引入动态分发；添加不必要的 `Send`、`Sync`、`'static` 或 `Clone` bound；用 `panic!`、`unwrap()` 或 `expect()` 替代显式错误传播；引入 unsafe；添加隐藏的可变全局状态；在不评估下游消费者的情况下改变公开签名；没有证据就声称 API 兼容性、测试成功或性能改进；把说明性示例当作实际工作区的已验证描述。

改变 API 之前，AI 辅助工作必须检查相关 crate 文档、依赖关系、现有实现与实际调用点。改变 API 之后，它必须检查结果差异并报告运行了哪些相关检查、哪些仍待完成。当证据不可用时，说明该限制，而不是假定仓库符合提议标准。

## 8. 测试策略与质量门

### 8.1 测试哲学

工作区应遵循五项原则。

**测试契约而非实现琐事：** 测试应验证外部可观察行为、已记录不变量与领域契约。它们不应不必要地依赖私有辅助名、内部调用序列、偶然分配模式或其他在有效重构中可能改变的细节。当检查实现细节是验证关键不变量最有效的方式时，内部测试可以检查它们。

**优先独立证据：** 在可行时，将结果与独立于被测实现的参考比较。示例：作为优化张量算子参考的简单标量实现；小矩阵的手算结果；梯度验证的有限差分近似；格式兼容性的已知序列化夹具；验证数值行为的独立实现。比较共享同一底层缺陷的两条代码路径不能建立独立正确性。

**在最低有用层测试：** 张量形状不变量主要属于 tensor 测试。CPU 内核的数值行为主要属于 cpu 测试。模型的参数映射主要属于 models 测试。应用集成属于集成或应用级测试。高层测试应验证组件协同工作，而不是复制每个低层测试。

**使失败可诊断：** 失败的测试应识别：被测操作；相关输入或最小化夹具；预期行为；实际行为；相关时的数值容差或不变量。测试应以可操作的诊断失败，而不是无法解释的布尔断言。

**保持测试与风险成比例：** 简单的元数据访问器不需要与 checkpoint 写入器、优化器更新或数值敏感内核相同的测试机制。测试努力必须反映失败影响、复杂度、外部暴露与检测回归的难度。

### 8.2 测试分类

使用能确立所需契约的最小测试类别，然后在集成风险证明合理时添加更广泛测试。

| 测试类别 | 主要目的 | 典型位置 |
| --- | --- | --- |
| 单元测试 | 验证小函数、类型或不变量 | 仓库根 `tests/`，仅公开 API |
| 契约测试 | 验证公开行为与 trait 契约 | 仓库根 `tests/` 与专门契约套件 |
| 属性测试 | 在生成输入上验证一般属性 | crate 测试或专门测试模块 |
| 数值测试 | 对照参考验证浮点结果 | tensor、cpu、autograd、nn、optim |
| 回归测试 | 防止已知缺陷回归 | 受影响组件附近 |
| 集成测试 | 验证跨公开 crate 边界的交互 | 仓库根 `tests/`（由工作区根包拥有） |
| 格式兼容性测试 | 验证定义数据格式的读写 | format、checkpoint |
| 端到端测试 | 验证完整用户可见工作流 | 应用或工作区集成测试 |
| 架构测试 | 验证依赖与分层规则 | 脚本、CI 检查或专门验证工具 |
| 基准 | 在受控条件下测量性能 | 仓库根 `benches/`，共享工作负载在 `crates/bench` |
| 压力测试 | 检验持续负载与资源行为 | 专门测试目标 |
| 故障注入测试 | 验证依赖或操作失败时的行为 | 基础设施与编排测试 |

这些类别互补。基准不确立正确性，单元测试不确立跨工作区的正确集成。

### 8.3 工作区测试组织

工作区应按归属与范围组织测试。

**物理布局（当前）：** 仓库根 `tests/` 下的全部套件是单一集成测试目标 `tests/it/` 的模块。`tests/it/main.rs` 以 `mod` 声明各套件与共享夹具 `tests/it/common.rs`，因此 `tests/` 只产生一个测试二进制，而非每个套件文件一个；各套件经 `crate::common` 访问共享夹具。整合的理由、被否决方案与测量见 §8.22。2026-10-10 之前的历史验证记录仍以 `tests/<name>.rs` 书写，其当前磁盘位置为 `tests/it/<name>.rs`。

**单元测试：** 单元测试位于仓库根 `tests/`，仅通过 crate 的公开 `pub` 接口触达 crate。`crates/*/src` 下的生产源码不得包含 `#[cfg(test)]` 模块、`#[test]` 函数或 `#[cfg(test)]` 门控项（见本章黑盒契约优先测试决策；门为 `scripts/checksrctests.sh`）。

单元测试用于：公开不变量与契约；通过公开入口可达的小算法；校验逻辑与错误变体；通过公开接口可达的边界条件；通过公开接口可观察的局部状态转换。

无法从公开接口可达的行为不被测试；要么为它设计合法公开入口，要么将不可达逻辑作为死代码删除。保持夹具小且确定。

**集成测试：** 集成测试应行使公开接口与允许的 crate 交互。它们应用于验证：公开 API 行为；trait 互操作；跨 crate 数据契约；抽象边界的错误转换；模型加载与推理工作流；checkpoint 保存与加载工作流；训练与优化器集成。集成测试不得成为绕过预期 crate 边界的机制。

**共享测试工具：** 当多个测试套件真正需要时，共享夹具与辅助可以放入 testkit。testkit crate 不得成为生产依赖。测试辅助应小且显式。避免构建隐藏被测行为的大型测试框架。

**测试数据：** 夹具应：足够小以便例行 CI 执行；确定；清晰命名；在兼容性重要时版本化；外部来源时适当许可；二进制结构不自明时有文档。大型模型与数据集不应要求用于每次单元测试运行。例行测试使用小合成夹具，把较大产物留给专门集成或发布验证。

**避免重复测试归属：** 契约应有清晰的主要所有者。例如，tensor 应确立张量形状语义。模型集成测试可以验证模型遵守这些语义，但无需复制每个张量边界测试。

### 8.4 单元测试要求

单元测试应一次验证一个主要行为。对每个非平凡函数，考虑：典型有效输入；支持的最小与最大值；空输入（若允许）；无效输入；边界转换；算术溢出；错误传播；失败后的状态保持。并非每个函数都需要每个类别。测试用例应按函数契约选择。

**避免过大的测试：** 检验数十个无关行为的测试难以诊断。当测试验证独立契约或因无关原因失败时拆分它们。当交互本身是预期主题时，测试可以覆盖完整工作流。

**测试命名：** 测试名应描述条件与预期结果。优先使用如下名称：

```text
rejects_incompatible_dimensions
returns_error_when_element_count_overflows
preserves_parameters_after_failed_validation
loads_supported_checkpoint_version
```

避免模糊名称如 `test_basic`、`test_all` 或 `works`。

**避免只镜像实现的测试：** 如果一个测试只是重复生产算法并比较两者结果，而两者可能共享同一缺陷，则不应如此。优先使用直接期望值、独立派生的参考、不变量或刻意更简单的算法。

### 8.5 边界与对抗性测试

对处理维度、索引、长度、偏移、大小或外部提供元数据的组件，边界测试是强制的。

**张量边界（在适用时测试）：** 空形状；标量与 rank-one 张量；支持的最小维度；接近配置限制的大维度；形状不匹配；无效索引；无效置换；带检查的元素数量算术；若 API 允许的零尺寸维度；空归约与广播边界情形；非连续布局（若支持）。不要假定零尺寸张量普遍有效或无效。行为必须遵循已记录的张量契约。

**输入解析边界：** 对解析器与反序列化器，测试：空输入；截断输入；无效头部；无效长度与偏移；不支持版本；不一致元数据；意外尾随字节（如相关）；允许的最大输入大小；无效编码或格式错误记录。格式错误的输入必须产生已记录错误，而不是 panic 或不受控资源消耗。

**整数算术：** 任何可能溢出并影响分配、索引、布局或文件访问的计算都应获得显式边界覆盖。示例：元素数量；字节大小；步长；偏移计算；缓冲长度；批大小乘积；checkpoint 段边界。测试应直接检验溢出条件，而不是依赖不切实际的大分配。

**边界覆盖依赖契约：** 不要仅为满足测试清单而引入任意行为。若边界不受支持，实现应显式拒绝它，测试应验证该拒绝。若边界受支持，测试应验证其行为。

### 8.6 数值正确性

数值正确性是张量计算、神经网络操作、自动微分、优化与模型执行的一等要求。数值上看似合理的结果不一定正确。

**参考实现：** 数值上非平凡的算子应与独立参考比较。合适参考可包括：手算小用例；简单标量算法；更高精度计算；有已记录契约的可信实现；独立派生的数学恒等式。参考必须匹配预期数学操作，包括形状、归约、广播与边界情形语义。

**绝对与相对容差：** 对浮点结果，常见比较规则是：

$$
|a-b| \leq \epsilon_{\mathrm{abs}} + \epsilon_{\mathrm{rel}}\,|b|
$$

其中：$a$ 是实际结果；$b$ 是参考结果；$\epsilon_{\mathrm{abs}}$ 是绝对容差；$\epsilon_{\mathrm{rel}}$ 是相对容差。该公式是起点，不是通用策略。容差值必须按 dtype、算法、归约长度、预期数值条件与后端行为选择。测试不得仅为让错误实现通过而使用过松容差。

**NaN 与无穷：** 涉及 NaN 的比较需要显式处理，因为普通相等检查对它们的表现不同于有限值。测试应定义以下行为的预期：NaN 输入；正负无穷；溢出与下溢；除以零；退化归约；数学结果对特定输入未定义的操作。这些值是被接受、传播还是拒绝必须遵循算子契约。

**累加顺序：** 浮点加法不满足结合律。不同有效实现可能因以下原因产生略不同结果：向量化；并行归约；不同累加精度；不同操作顺序；编译器与后端行为。测试应验证在合理容差内的数学契约，而不是在没有特定要求时要求按位相等。对显式确定操作或序列化产物，可能要求按位可复现。此类要求必须单独记录。

**dtype 覆盖：** 每个支持的 dtype 应为其相关行为有适当测试。不要仅因操作对其能编译就声称支持该 dtype。当操作对某 dtype 不支持时，测试已记录的拒绝行为。

**数值稳定性：** 有已知稳定性顾虑的算法应包含代表性困难输入的测试。示例：大与小的量级；易对消的求和；softmax 中的极端 logits；归一化中的小方差；近似奇异或病态输入；长归约；接近零的梯度。这些测试应针对现实失败模式，而非仅任意随机数。

### 8.7 自动微分与梯度测试

自动微分需要验证前向值与梯度行为。

**前向正确性：** 每个可微算子必须有覆盖其支持输入域的前向数值测试。

**梯度正确性：** 每个新的可微算子应与独立梯度参考比较。在可行时使用有限差分：

$$
\frac{\partial f}{\partial x_i}
\approx
\frac{f(x+h e_i)-f(x-h e_i)}{2h}
$$

其中 $e_i$ 是分量 $i$ 的单位方向。有限差分是近似，对病态函数、不适当步长或非光滑点可能不准确。测试输入与步长必须相应选择。

**必需考量：** 梯度测试应覆盖：代表性输入；形状一致性；梯度维度；与参考的数值一致；广播行为；归约行为；多条路径对梯度有贡献时的累加；定义处的零或边界梯度；不支持输入的错误行为。

**不可微点：** 对非光滑函数，测试必须遵循已记录的导数约定或定义域限制。不要在有导数未定义的点与有限差分结果比较，然后把不一致当作实现缺陷的证据。

**无意外状态泄漏：** 测试应验证重复前向与反向操作不会无意在共享模型参数中保留请求特定或图特定状态。图状态、梯度缓冲与中间值的预期生命周期必须遵循 autograd 契约。

### 8.8 算子验收标准

每个新张量或计算算子必须包含：1. 边界测试——支持边界、无效输入、形状规则与（如适用）溢出条件。2. 数值测试——与合理独立参考的比较。3. 至少一个基准——代表性工作负载的可复现基线。

此外，算子应包含：dtype 覆盖；布局覆盖；错误路径测试；适用不变量的属性测试；若算子参与自动微分则包含梯度测试；若改变公开或跨 crate 契约则包含集成测试。

基准要求不意味着每个新算子必须展示性能改进，而意味着其性能特征可被测量。新算子不因其前向路径产生一个预期结果就算完成。

### 8.9 基于属性与蜕变测试

当操作在宽输入空间上有有用的一般不变量时，应使用基于属性的测试。潜在属性包括：形状保持；元素数量一致性；往返序列化；置换与逆置换行为；恒等操作；在有效数值容差内的代数恒等式；等价布局之间的一致性；确定操作对确定性输出的确定性。

**生成输入：** 生成输入必须尊重被测属性的前置条件。若有意生成格式错误输入，预期行为必须显式。生成器应保持有界，使普通测试运行不会分配不受控内存或运行不可预测时长。

**蜕变测试：** 当直接参考结果昂贵或不可用时，蜕变测试验证相关执行之间的关系。示例：应用逆置换恢复原张量；保存并加载支持的 checkpoint 保留已记录内容；恒等变换保留预期输出；在契约保证等价时，等价输入表示产生等价结果。关系本身必须有数学与语义依据。

**可复现性：** 生成测试用例失败时，失败应保留足够信息以复现该用例，包括所选测试框架支持的 seed 或最小化输入。当生成用例暴露可能难以复现的真实缺陷时，应将其提升为聚焦回归测试。

### 8.10 回归测试

每个可复现的 bug 修复必须包含回归测试，除非测试确实不切实际或无法有意义地检测复现。若无法添加回归测试，变更描述必须解释原因并识别替代验证方法。

好的回归测试：复现原始失败；对缺陷行为失败；对修正行为通过；验证预期契约而非确切补丁实现；保持足够小以便诊断。避免因受影响代码路径从未被执行而通过的测试。对数值回归，测试应识别相关输入域与预期容差。对性能回归，使用基准与测量策略，而不是把普通测试时长当作回归证据。

### 8.11 集成与端到端测试

集成测试验证组件跨公开接口正确交互。工作区应为关键工作流维护一小套可靠端到端测试。

**模型加载与推理：** 加载支持的小夹具；校验模型配置；运行确定性或适当受控的推理用例；验证输出结构与相关数值属性；行使已记录的失败路径。

**Checkpoint 往返：** 构造小已知模型状态；写入 checkpoint；读回；按格式契约验证元数据、参数名、形状、dtype 与值；行使格式错误或不兼容 checkpoint 行为。

**训练工作流：** 构造小确定性数据集；执行有界训练工作流；验证预期状态变化发生；检查相关优化器或梯度不变量；在适用时验证 checkpoint 或取消行为。

**Tokenizer 与数据管线：** 处理小已知输入；按公开契约验证 token ID、偏移或解码输出；行使格式错误输入与相关边界情形。

端到端测试应使用验证交互的最小夹具。它们不应下载大模型、要求外部网络服务或在例行本地开发中消耗过多资源，除非明确归类为单独集成套件。

### 8.12 错误路径与故障注入测试

错误行为是契约的一部分，必须在相关时验证。

测试应覆盖：无效输入；缺失资源；权限或 I/O 失败；损坏序列化数据；不支持操作；资源限制拒绝；后端初始化失败；取消与超时；部分写入或中断工作流；重试耗尽；失败后清理。

**故障注入：** 在可行时，使用 trait、受控测试替身、临时文件或其他显式接缝来模拟失败。故障注入必须保持面向测试，不得仅为迎合测试而扭曲生产架构。当小的 trait 或局部测试替身足够时，不要引入宽泛的依赖注入框架。

**状态一致性：** 对改变状态的操作，测试应验证失败后仍成立的内容。示例：失败的校验不改变模型参数；失败的 checkpoint 操作不把不完整产物作为已提交发布；被取消的请求不无限期继续产生用户可见输出；失败的优化器操作遵循其已记录的部分更新语义。不要断言实现实际未提供的回滚保证。

### 8.13 确定性与测试隔离

例行测试应是确定的。测试不得依赖未指定顺序、不受控全局可变状态或偶然计时假设。

**随机性：** 当可复现性重要时，随机化测试应使用受控 seed。当失败依赖随机输入时，应报告 seed 与相关生成器配置。不要以让测试看似全面却反复只行使一个平凡用例的方式固定 seed。有用策略可结合确定性回归用例与有界随机探索。

**并行执行：** 当 Rust 测试 harness 并发运行测试时，测试应保持正确。避免在无适当隔离的情况下共享可变文件、环境变量、端口或全局状态。需要独占资源的测试应使用显式隔离或被分配到单独控制的测试目标。

**时间与并发：** 避免使用任意 sleep 作为同步机制。优先使用显式同步原语、有界截止时间、确定性状态转换与受控测试替身。并发与取消测试应使用超时以避免挂起套件，但超时必须作为安全边界，而不是正确性的主要证明。

**网络访问：** 例行单元测试不得要求外部网络访问。真正需要网络或外部服务的测试应被隔离、清晰标识，并在默认快速本地测试循环之外，除非项目明确选择其他方式。

**环境假设：** 当无法避免时，测试必须记录所需外部工具、硬件、环境变量或操作系统特性。无法在特定环境运行的测试必须被报告为未执行或不支持，而不是通过。

### 8.14 架构与依赖测试

工作区架构规则应尽可能自动强制。检查应覆盖：允许的 crate 依赖方向；禁止的依赖环；对 testkit 的生产依赖；对仅基准组件的生产依赖；泄漏到核心 crate 的应用层依赖；意外依赖添加；禁止的 unsafe 使用；仓库特定源码与构建约束。检查可以使用 Cargo 元数据、清单检查、源码扫描或其他适当范围机制。

**优先结构化检查：** 依赖检查应检查解析后的依赖图，而不是仅从文件名或源码导入推断架构。对依赖元数据无法确立的要求，源码扫描可以补充图检查。

**避免脆弱策略检查：** 策略脚本应有已记录目的、确定性输出与对其自身行为的测试。不要创建会拒绝合法代码却错过其意图检测的禁止情形的宽泛正则检查。

**架构变更：** 当变更修改 crate 边界或引入依赖时，评审者必须验证实际依赖图。文档图不是解析后的 Cargo 图符合要求的证据。

### 8.15 基准与性能验证

基准是与正确性测试不同的证据来源。每个新算子必须至少有一个基准。当存在有效基线时，性能敏感变更应包含前后测量。

**基准要求：** 基准应记录：操作与工作负载；输入维度与 dtype；布局与相关配置；编译器与 Rust 工具链；构建 profile 与特性开关；硬件与操作系统；预热与测量策略；样本数或迭代策略；报告的统计量与变异；相关时的分配或内存行为。

**基准隔离：** 基准应避免计时区域内的无关工作。例如，内核基准不应意外包含模型加载、文件 I/O 或夹具生成，除非这些成本是有意属于被测操作的一部分。

**正确性先于性能：** 实现必须先满足其正确性契约，基准结果才能作为采纳依据。返回错误值的更快实现是回归，不是优化。

**性能声明：** 使用本文《性能工程与基准》章节定义的性能状态词汇。不要仅凭代码检查、直觉或单次有噪声的观察就声称性能改进。完整测量与报告策略见该章节。

### 8.16 测试命令与验证级别

确切命令必须遵循工作区实际 Cargo 配置、工具链、支持目标与特性策略。以下是候选基线检查，在作为强制 CI 命令之前必须对照仓库验证。

格式化：

```sh
cargo fmt --all -- --check
```

工作区编译：

```sh
cargo check --workspace --all-targets
```

Lint：

```sh
cargo clippy --workspace --all-targets -- -D warnings
```

单元与集成测试：

```sh
cargo test --workspace
```

这些命令可能需要额外的特性、平台或目标特定调用。成功的命令只验证它实际覆盖的目标与配置。

**验证级别：** 开发工作流应使用多个验证级别。

- **级别 1 聚焦验证：** 为变更组件运行最小相关测试与检查。
- **级别 2 crate 验证：** 运行受影响 crate 的测试与相关集成测试。
- **级别 3 工作区验证：** 运行适用的工作区编译、lint 与测试检查。
- **级别 4 专项验证：** 在变更需要时运行数值压力测试、架构检查、故障注入、基准或硬件特定测试。
- **级别 5 发布验证：** 运行项目定义的发布套件以验证兼容性、关键工作流与支持配置。

并非每次编辑都需要每个级别。所选验证范围必须由变更的风险与契约证明合理。

### 8.17 CI 与持续验证

持续集成应为每个变更提供可靠、可复现的证据。CI 流水线应优先快速、高信号的检查，再运行昂贵测试。

推荐的逻辑顺序：1. 格式与静态策略检查。2. 编译与 lint。3. 聚焦单元与契约测试。4. 工作区集成测试。5. 专项数值与架构测试。6. 计划或专门压力测试。7. 基准收集与性能回归分析。8. 发布验证。确切阶段取决于仓库大小、可用硬件与 CI 能力。

**必需与可选检查：** 每个检查应分类为：每个变更必需；对选定路径或 crate 必需；发布前必需；计划运行；信息性。必需检查不得仅因不方便就静默变为可选。

**失败的基础设施与失败的测试：** CI 必须区分：测试断言失败；编译失败；超时；不可用依赖或服务；不支持的平台；基础设施失败。基础设施失败不确立代码不正确，但也不确立代码正确。

**不稳定测试：** 不稳定测试是验证系统的可靠性缺陷。当发现测试不稳定时：1. 保留失败证据。2. 识别非确定性来源。3. 尽可能修复原因。4. 在需要时添加隔离或有界同步。5. 记录任何临时隔离。6. 跟踪补救。反复重跑不稳定测试直到通过不得被视为可靠验证策略。

### 8.18 测试维护

测试是生产工程资产，必须与实现变更一同维护。

**重构：** 有效重构应保留现有契约测试所确立的行为。当测试在重构后失败时，判断是：实现引入了回归；测试编码了未记录实现细节；预期契约改变；参考实现或测试夹具错误。不要自动改变期望结果以匹配新实现。

**移除测试：** 当契约已过时、与更强证据冗余或无法提供有意义验证时，可以移除测试。移除不得在没有明确理由的情况下留下关键行为未测试。

**测试性能：** 默认本地测试循环应保持足够快以鼓励频繁执行。昂贵测试应按范围或执行剖面分离，同时保留其必须运行时间的明确要求。当测试运行时间成为重要工程瓶颈时，应测量它。

**测试辅助：** 测试辅助应减少真实重复，而不隐藏前置条件、副作用或失败行为。避免静默用默认值替换无效夹具数据或吞噬搭建失败的辅助。

### 8.19 AI 辅助测试规则

AI 编码代理必须把测试输出与仓库状态当作证据，而非假设。AI 代理不得：未执行就声称测试通过；发明基准结果；因编译成功就声称完整覆盖；仅为使 CI 变绿而不理解失败就移除失败测试；没有数学依据就弱化数值容差；仅为绕过失败就把带类型错误断言替换为更弱断言；添加从未触达受影响代码路径的测试；不检查相关依赖图就声称架构合规；修改无关测试以隐藏回归。

当测试执行不可用时，代理必须说明哪些检查未运行及原因。当测试失败时，报告应包含相关失败、有证据支撑时的可能原因，以及下一步验证。

AI 生成的测试必须评审其独立于生产实现。仅重现同一算法的测试不自动是有用参考。

### 8.20 黑盒契约优先测试决策

**状态：** 已接受。**日期：** 2026-10-10。**范围：** 每个工作区 crate 的测试放置、测试可见性、死代码策略与生产诊断插桩。

**背景：** 工作区此前把大批单元测试内联在 `crates/*/src` 的 `#[cfg(test)]` 模块中，而仓库根 `tests/` 只有少量跨 crate 集成套件（迁移前的模块数与用例数未保留可复现出处，故此处不引用具体数字）。根套件已通过公开接口行使 crate；内联模块是例外。契约优先的长期基础设施要求相反的默认：先固定公开契约，仅通过它测试，把公开接口当作唯一可测试面。两点具体成本驱动它：1. 测试维护随接口而变——私有辅助重命名时，每个触及它的内联测试都必须改变；绑定到公开契约的测试在内部重构中不变。2. 深度白盒测试掩盖接口缺口——通过私有路径构造非法内部状态的测试，无法证明调用方是否能到达该状态；若边界分支无法通过公开接口到达，接口就无法防御它。

本记录使黑盒测试成为规范默认，取代内联单元测试规则，并定义保持黑盒失败可观测的诊断接缝。

**决策：**

1. **生产源码不含测试。** `crates/*/src` 不得包含 `#[cfg(test)]` 模块、`#[test]` 函数或 `#[cfg(test)]` 门控项。所有单元、集成、回归与基准测试位于仓库根 `tests/`（基准按 `cargo bench` 所依赖的 Cargo 约定位于 `benches/`）。
2. **测试仅使用公开面。** 测试必须通过 crate 的 `pub` 项触达它。不得调用私有函数、读取私有字段或命名私有类型。`testkit` 是唯一允许的共享测试依赖，且保持非生产 crate。
3. **不为测试放宽公开接口。** 暴露内部类型或添加唯一消费者是测试的 `pub` 项被禁止（见本文《公开 API 设计与演进》章节的可见性小节）。需要仅测试 hook 的 crate 设计一个带自身契约的合法公开入口，或不测试该路径。
4. **不可达私有逻辑是死代码。** 若内部逻辑无法从公开接口到达，则将其删除而非测试。可达但不可直接构造的逻辑不是死代码：其行为通过到达它的公开入口断言。
5. **边界路径是设计进去的，而非绕开测试。** 当契约有极端或例外分支时，接口必须暴露让调用方到达它的参数或入口，使该分支可通过公开接口触发。被推迟的替代方案见本小节"被否决的替代方案"。
6. **测试验证预先声明的契约；覆盖不是目标。** 测试必须断言已记录的输入/输出或错误契约。仅为提高覆盖率数字而写、或断言实现细节而非契约的测试是缺陷。
7. **生产携带可切换诊断接缝。** 生产代码可以在决策点发出轻量 `tracing` 事件与 span。这是生产诊断能力，不是测试代码。它默认禁用，可在运行期无需重新编译即启用。

**迁移策略：** 迁移分阶段进行，门 `scripts/checksrctests.sh` 强制棘轮：仍含内联测试的每个文件列在 `scripts/srctestbaseline.txt`；含内联测试但不在基线的文件使门失败（禁止新的内联测试）；基线条目没有剩余内联测试也使门失败（已迁移文件必须从基线移除）。棘轮只会收紧。当基线为空时，禁令绝对。试点 crate `lib` 在此变更中迁移；其余 crate 每个提交迁移一个。

**诊断接缝：** `tracing` 与 `tracing-subscriber` 已在工作区依赖中声明。接缝为：生产决策点发出 `tracing::trace!`/`debug!` 事件；请求或操作范围的工作使用 `#[tracing::instrument]` span。真实异常使用 `warn`/`error`。热路径仅在 `trace`/`debug` 发出，使默认过滤器以最小成本丢弃它们（PF2）。开关是 subscriber：未安装 subscriber 时事件被丢弃；应用（`cli`、`serve`）通过安装带 `EnvFilter`（`RUST_LOG`）的 `tracing_subscriber` layer 来启用它们。不涉及重新编译与仅测试代码。该接缝使黑盒失败可定位：测试断言公开契约，trace 报告产生结果的内部分支。

**被本记录取代的规则：** 本记录取代以下位置的 inline-unit-test 规则，且必须在同一变更中更新：本文《测试策略与质量门》章节的单元测试位置与工作区测试组织小节；本文《公开 API 设计与演进》章节可见性小节的最后一句；AGENTS.md 关于测试组织的条目；本章集成测试与基准整合决策中"crate 局部覆盖现在仅内联单元测试"的后果。整合记录的其余部分（仓库根的集成测试与基准）仍然成立并在此强化。

**被否决的替代方案：**

- **为私有辅助保留内联测试。** 否决：它保留了该强制令要移除的耦合。私有辅助的行为通过到达它的公开入口断言，否则该辅助就是死代码。
- **把辅助暴露为 `pub` 以迁移其测试。** 被决策 3 否决：它为测试便利放宽契约，并创建没有真实消费者的兼容承诺。
- **每个测试门控的 `#[cfg(test)]` "接缝"访问器。** 否决：它在生产源码中重新引入仅测试代码，并依赖 `cfg(test)`，而这正是要被移除的东西。
- **用编译期 `feature = "diagnostics"` 替代运行期 tracing。** 否决，改用 subscriber 开关：特性开关需要重新构建才能启用，而 subscriber 可在运行中的部署中切换。

**后果：** 工作区只有一个测试面：公开契约。内部重构不再破坏测试。迁移全部内联单元测试需要为每个被断言行为提供真实公开入口。在没有入口的地方，要么该行为已通过另一公开路径被间接覆盖，要么接口获得合法参数化入口（决策 5），要么逻辑作为死代码被删除（决策 4）。`testkit` 作为共享黑盒夹具与参考提供者而增长。生产代码在需要可观测性的 crate 中获得一个小的、默认禁用的诊断依赖。

**验证：** 于 2026-10-10 对全工作区执行（macOS 27.0.1、`aarch64-apple-darwin`、rustc 1.99.0、edition 2024）：

```sh
bash scripts/checksrctests.sh      # exit 0；0 个文件待迁移
bash scripts/check.sh              # exit 0（fmt、clippy、naming、ratchet、thresholds、doc）
cargo test --workspace --locked    # 所有套件通过，0 失败
cargo test -p llm --test diagnostics  # 2 通过（可切换诊断接缝）
```

全部十九个 crate 已迁移到 `crates/<crate>/src` 中零 `#[cfg(test)]`——`lib`、`api`、`context`、`data`、`cpu`、`testkit`、`tensor`、`checkpoint`、`bench`、`autograd`、`optim`、`nn`、`models`、`format`、`infer`、`cli`、`serve`、`train`、`tokenizer`。`scripts/srctestbaseline.txt` 为空，因此棘轮禁令现在是绝对的。迁移由 `scripts/migrateinline.py`（带 `scripts/_rustscan.py` 词法花括号扫描器）与 `scripts/finalizecrate.py` 驱动，它们在迁移套件编译后剥离源码。

**诊断接缝（验证）：** 接缝（决策 7）接入 `infer`、`train`、`checkpoint`、`serve` 与 `cli`：工作流决策点发出 `debug!`/`trace!`，应用（`cli::runcli`、`httpserver::serve`/`serveone`）安装从 `RUST_LOG` 读取的 `tracing_subscriber` `EnvFilter`（默认 `warn`）。`tests/diagnostics.rs` 证明无需重新编译即可切换：同一公开 `loadcheckpoint` 调用在 `DEBUG` subscriber 下发出 `"checkpoint loaded"` 事件，在 `WARN` subscriber 下抑制它。

### 8.21 集成测试与基准整合决策

**状态：** 已接受。**日期：** 2026-10-10。**范围：** 仓库根 `tests/`、`benches/`、根 `llm` 包清单，以及测试或基准被移动的各 crate 清单。

**背景：** 仓库级指南与本文《测试策略与质量门》章节把跨 crate 集成测试放在仓库根 `tests/`、基准放在仓库根 `benches/`（共享工作负载在 `crates/bench`），而 crate 内联单元测试留在其模块中。工作区布局决策确立了根 `llm` 包 + 工作区机制，并把 Layer 0/1 套件（`apicontract`、`cpucontract`、`tensorcontract`、`crosscrate`）以及 `autograd`、`nn`、`models` 套件移到根 `tests/`，其基准移到根 `benches/`。其余 crate（P4–P12：`tokenizer`、`format`、`checkpoint`、`context`、`infer`、`data`、`optim`、`train`、`serve`、`cli`）各自由并发 worker 构建，为避免在构建中途编辑共享根清单，把其集成测试与 `optim` 基准 crate 局部放在 `crates/<name>/tests/` 与 `crates/optim/benches/`。那些每 crate ADR 把该放置记录为刻意的、阶段范围的偏离，并说明后续整合负责根目录。本记录就是该整合。

**决策：**

1. **把每个 crate 局部集成套件移到仓库根 `tests/`。** `crates/{tokenizer,format,checkpoint,context,infer,data,optim,train,serve,cli}/tests/` 不再存在。被移动的文件为 `tokens`、`artifact`、`roundtrip`、`context`、`generation`、`isolation`、`pipeline`、`optim`、`cancellation`、`lossdecrease`、`trainingresume`、`service`、`server` 与 `cli`。名称含 `_` 的文件被重命名为无分隔符形式（`loss_decrease.rs` → `lossdecrease.rs`、`training_resume.rs` → `trainingresume.rs`；模型前向套件同理由含下划线的原名去分隔符而来）。
2. **把 `optim` 基准移到仓库根 `benches/`。** 该 crate 不保留 `[[bench]]` 目标与 `criterion`/`checkpoint` 开发依赖；`checkpoint` 往返覆盖现在位于根 `optim` 套件，测试专用根包可直接触达它。

## 9. 性能工程与基准

### 9.1 性能工程原则

**先测量后优化：** 每个非平凡优化都应以证据开始，证明受影响操作对工作负载成本有实质贡献。可接受证据可包括：可重复基准；CPU profile；分配测量；硬件性能计数器；执行 trace；代表性端到端工作负载；隔离疑似瓶颈的受控实验。疑似瓶颈是假设，不是已验证事实。

**优化实际目标：** 不同工作负载有不同性能目标。例如：CLI 启动可能优先首个有用输出的时间；交互式推理可能优先首 token 时间与 token 间延迟；离线生成可能优先总吞吐；训练可能优先步时间与每秒完成的有用工作；checkpoint 可能优先完成时间、存储开销与恢复保证；张量操作可能优先延迟、吞吐、内存流量或分配开销。预期目标必须在优化前说明。

**优先最简单有效实现：** 优先满足所需性能目标的简单实现，而非优势未经证实或可忽略的更复杂实现。没有清晰理由时，不要引入自定义线程池、复杂分发系统、缓存层、专门内存管理或额外依赖。

**保持抽象边界：** 性能工作必须尊重既定的 crate 边界。底层优化不得仅为访问配置、模型状态、请求上下文或应用行为而引入对高层 crate 的依赖。在现有接口足够时使用它们。仅当变更由真实契约或性能需求证明合理时才改变 trait 或公开接口。

**考虑总成本：** 更快的内核可能增加分配、内存使用、初始化时间、代码大小或下游处理成本。评估相关权衡，而不是把单个计时数字当作完整结果。

### 9.2 性能目标与指标

每个重要的性能调查应识别其主要指标与相关次要指标。

| 目标 | 主要指标 | 有用次要指标 |
| --- | --- | --- |
| 操作延迟 | 每操作时间 | 变异、分配 |
| 吞吐 | 每秒操作数 | CPU 利用率、内存带宽 |
| 模型推理 | 端到端延迟或每秒 token 数 | 首 token 时间、token 间延迟 |
| 训练 | 每步时间或每秒有用样本数 | 内存使用、同步开销 |
| 内存效率 | 峰值或稳态内存 | 分配次数、保留容量 |
| Checkpoint | 保存或加载时间 | 处理字节数、峰值内存 |
| 启动 | 到就绪的时间 | 初始化工作、分配 |
| 可扩展性 | 随负载增加的吞吐或延迟 | 争用、尾延迟 |
| 编译 | 构建或编译时间 | 增量重建成本 |

并非每个指标适用于每个操作。基准规范应区分主要验收指标与诊断指标。

**延迟与吞吐不同：** 延迟衡量操作耗时；吞吐衡量单位时间完成的工作量。某个变更可能提升吞吐而恶化单请求延迟，尤其当批处理或并发变化时。指标必须匹配实际目标。

**平均延迟对变化负载不足：** 对有实质延迟变异的系统，当样本数与测量方法支撑时报告相关百分位如 p50、p95、p99。当样本量不足或工作负载不具代表性时，百分位不得被视为可靠估计。

**内存指标：** 内存测量应在可行时区分：峰值常驻内存；稳态常驻内存；活跃张量或缓冲存储；临时分配；分配次数；保留容量；设备内存（若存在加速器后端）。分配次数减少不自动意味着更低峰值内存或更好端到端性能。

### 9.3 基准分类

工作区应维护多个层级的基准。

**微基准：** 隔离小操作或开销。示例：张量索引；形状校验；逐元素操作；归约内核；矩阵乘法；分配与缓冲复用；数据转换；trait 分发开销。微基准对识别局部变化有用，但不确立端到端改进。

**算子基准：** 使用有代表性的形状、dtype 与布局，行使完整的公开或内部算子契约。每个新算子必须至少有一个基准。基准应表示有用工作负载，而不是人为有利的单一输入。

**管线基准：** 测量多个操作之间的交互。示例：分词与编码；批准备；前向与反向传播；优化器更新；checkpoint 序列化；模型加载与初始化。这些基准帮助识别单个算子基准无法揭示的成本。

**端到端基准：** 测量完整用户相关工作流。示例：加载模型并运行推理；生成固定数量 token；执行一个训练步；保存并恢复 checkpoint。当变更可能实质影响整体系统性能时应包含端到端测量。

**压力与扩展基准：** 检验在负载、并发或资源压力增加下的行为。它们应与例行微基准分离，并在系统运维需求证明合理时使用。基准不得仅因运行时间长而被标记为压力测试。

### 9.4 基准可复现性

基准结果只有在工作负载与测量条件被充分记录时才有意义。

**必需基准元数据：** 每个维护的基准应记录或可恢复：基准名与操作；输入维度与 dtype；相关时的张量布局与步长；相关时的批大小与序列长度；相关模型或数据集夹具；Rust 工具链版本；编译器版本与优化配置；构建 profile；启用的 Cargo 特性；目标平台与架构；CPU 型号与相关硬件配置；相关时的操作系统与内核信息；基准框架与版本；预热策略；测量时长或迭代策略；样本数；报告的统计量；相关工作负载特定设置。确切元数据取决于基准。若环境被集中记录，则无需为每个结果重复无关字段。

**控制环境：** 在可行时：使用优化构建；避免无关的 CPU 密集后台工作；避免同时运行竞争相同资源的基准；保持电源与热条件合理稳定；在比较之间保持编译器标志与特性一致；在基线与候选测量之间避免改变工作负载数据；当线程数与亲和策略影响结果时保持一致。完美环境隔离并非总能实现。任何实质限制必须记录。

**预热：** 当首运行效应不是预期指标的一部分时应使用预热。潜在首运行效应包括初始化、内存分配、缓存填充、惰性设置与运行期分发。若启动或冷缓存性能是实际目标，显式测量它而不是将其预热掉。

**重复测量：** 使用适合工作负载时长与变异的重复测量。非常短的操作可能需要批处理或重复迭代以减少计时器开销。长操作可能需要较少样本，但其变异与环境敏感性仍需考虑。不要在看到哪个样本数使结果看似有利后才选择样本数。

**记录失败尝试：** 若基准失败、超时、遭遇资源耗尽或产生无效输出，保留该结果作为失败或不完整运行。不要在没有已记录测量规则的情况下静默丢弃不便的样本。

### 9.5 基线与前后对比

性能改进需要有意义比较。

**基线选择：** 基线应表示相同或足够可比条件下的先前正确实现。接受比较前，验证：工作负载等价；正确性要求不变；编译器与构建设置可比；硬件与环境差异已理解；相关预热与测量策略匹配；没有无关代码变更主导结果。若无法确立这些条件，比较必须被限定为有限或无结论。

**实现前记录基线：** 对于计划的性能工作，在可行时于优化前记录基线。这降低实现后选择有利比较的风险。若不存在有效基线，在声称改进前建立一个。

**正确计算相对变化：** 对于越低越好的指标（如延迟）：

$$
\text{Reduction (\%)} =
\frac{T_{\mathrm{baseline}}-T_{\mathrm{candidate}}}
{T_{\mathrm{baseline}}}\times 100
$$

对于越高越好的指标（如吞吐）：

$$
\text{Increase (\%)} =
\frac{P_{\mathrm{candidate}}-P_{\mathrm{baseline}}}
{P_{\mathrm{baseline}}}\times 100
$$

这些计算描述观察到的相对变化。它们本身不确立统计显著性、实际重要性或因果归因。

**使用一致单位：** 始终说明单位。示例：每操作微秒；每请求毫秒；每秒 token 数；每秒样本数；峰值内存 MiB；每操作分配字节数。避免比较不同单位或不同被测工作定义的测量。

### 9.6 统计解释

性能结果会变化。解释必须考虑测量不确定性。

**报告变异：** 取决于基准，有用摘要包括：中位数；均值；标准差；四分位距；相关百分位；置信区间。没有单一统计量普遍适用。对有噪声或偏斜的延迟分布，中位数与百分位可能比均值信息量更大。对条件稳定的吞吐测量，其他摘要可能合适。

**区分观察差异与可靠改进：** 单次运行略快的候选不一定普遍更快。当变异显著时，重复测量并使用适当比较方法。结论应区分：清晰且实际有意义的改进；清晰回归；小到运维上无关紧要的差异；不确定性阻止结论的结果。

**不要夸大精度：** 若测量只支持近似结果，报告近似结果。不要从不稳定测量或过度舍入的数据声称精确百分比改进。

**定义实际显著性：** 优化应有说明其重要的理由。统计上可检测的差异仍可能运维上无关。反之，当操作主导频繁执行的路径时，小的局部改进可能重要。接受决策应同时考虑证据与实际工作负载。

### 9.7 优化工作流

性能变更必须遵循有纪律的流程。

**步骤 1 定义目标：** 说明工作负载、主要指标、预期收益与相关正确性约束。避免没有可测量目标或已识别瓶颈的目标如"让代码更快"。

**步骤 2 建立基线：** 在已记录工作负载下运行现有正确实现。记录相关测量与环境。

**步骤 3 识别瓶颈：** 使用测量、profiling 或受控实验识别主导成本。可能瓶颈包括：过多算法工作；不必要分配；重复数据转换；差的内存局部性；冗余张量拷贝；同步开销；分发开销；低效批处理；不必要中间张量；过多初始化。不要仅根据源码外观假定瓶颈。

**步骤 4 形成可测试假设：** 描述提议变更为何应改进所选指标。例如：复用正确限定作用域的临时缓冲预期减少该算子重复执行中的分配开销，而不改变其数值结果或公开契约。假设应识别预期机制、受影响工作负载与可能权衡。

**步骤 5 做最小有效变更：** 优先选择检验假设的聚焦实现变更。不要在一份不可评审的补丁中合并无关重构、API 重新设计与性能调优。

**步骤 6 验证正确性：** 在解释性能结果之前运行相关单元、边界、数值与集成测试。未满足正确性要求的候选不得作为优化被接受。

**步骤 7 测量候选：** 使用可比设置运行同一基准。收集足够证据以理解观察到的差异及其变异。

**步骤 8 评估权衡：** 评审以下变化：延迟；吞吐；内存使用；分配行为；初始化成本；代码复杂度；相关时构建时间与二进制大小；跨 crate 耦合；错误处理；数值稳定性。

**步骤 9 决策：** 当证据支持目标且权衡可接受时保留变更。当改进缺失、不可靠、小到不足以证明复杂度合理，或伴随不可接受回归时，回退或重新设计。

**步骤 10 报告结果：** 记录基准方法、结果、局限与最终结论。不要用成功的测试运行替代性能证据。

### 9.8 张量与 CPU 内核优化

张量与 CPU 操作常主导计算，但局部速度本身不够。

**算法复杂度：** 在追求小常数因子优化之前，优先选择具有适当渐进成本的算法。若工作负载由低效算法主导，指令级调优可能无法解决问题的根本瓶颈。

**内存布局：** 张量性能取决于形状、步长、连续性与访问模式。优化工作应考虑：顺序与不规则访问；缓存局部性；已加载值的复用；临时缓冲；拷贝与物化；步长感知迭代；布局转换开销。除非 API 明确保证连续性，不要假定所有张量连续。

**分配与复用：** 重复分配在热路径中可能昂贵。缓冲复用在其保持所有权、并发安全与生命周期保证时可以引入。缓冲复用不得在模型权重中创建隐藏共享可变状态，也不得允许请求级数据在执行之间泄漏。

**向量化：** 在 profiling 识别出相关瓶颈后，可考虑编译器向量化与架构特定优化。不要假定为向量化手动重构代码比更简单实现更快。验证生成行为或对结果做基准。

**并行：** 并行执行对足够大的工作负载可以提升吞吐。它也可能引入：线程启动与调度开销；同步成本；争用；超额订阅；不稳定延迟；非确定性浮点累加；增加内存使用。仅当工作负载与测量证据证明合理时才引入并行。

**无多余复杂度：** 没有证据证明分发与维护成本合理时，不要为每个形状、dtype 或输入大小添加专门执行路径。少量有充分动机的路径优于不可管理的投机特例集合。

### 9.9 模型推理性能

推理性能必须在适合预期用例的层级评估。

**区分执行阶段：** 在相关时分别测量：模型加载；初始化；输入准备；分词；prefill；自回归生成；输出解码；端到端请求延迟。这些阶段有不同瓶颈。改进一个阶段不一定改进总请求时间。

**生成指标：** 对自回归生成，区分：首 token 时间；token 间延迟；总生成时间；每秒生成 token 数；端到端请求延迟。基准必须记录吞吐计算是否包含 prompt 处理。没有定义的 token 计数与计时约定的每秒 token 数不是可复现指标。

**固定工作负载：** 对于比较，控制或记录：模型产物与配置；prompt 长度；请求输出长度；批大小；采样或解码配置；tokenizer；预热；并发；线程设置；相关硬件与构建配置。若生成是随机的，尽可能使用确定性工作负载，或报告随机设置与局限。

**避免共享可变请求状态：** 推理优化不得把请求特定可变状态放入共享模型权重。缓存、临时张量、生成状态与取消信息必须有显式所有权与并发语义。任何缓存优化应定义容量、生命周期、驱逐行为与请求间隔离。

**比较等价输出：** 当优化改变执行顺序或数值行为时，在比较速度前验证所需输出契约。对确定操作，必须记录输出相等要求。对数值近似操作，使用合理数值容差与应用级验收标准。

### 9.10 训练性能

训练性能受计算与状态管理开销双重影响。相关成本可能包括：数据加载；批准备；前向计算；反向计算；梯度累加；优化器更新；同步；checkpoint。

**测量预期工作单元：** 训练基准应说明它测量：一次前向；一次反向；一次优化器更新；完整训练步；完整 epoch；端到端训练工作流。不要将完整训练步与排除部分工作的测量比较。

**固定工作负载：** 记录模型、批大小、序列长度、数据集夹具、优化器配置与相关数值设置。若变更改变执行的工作量，仅原始耗时可能误导。

**保持训练语义：** 更快的训练路径不得静默跳过所需梯度计算、优化器更新、验证或状态持久化。性能变更必须保持已记录训练语义，包括相关状态更新与错误行为。

**Checkpoint 开销：** 当 checkpoint 实质影响训练吞吐时单独测量它。若引入异步 checkpoint，评估看似步时间改进与真实资源及完成成本。

### 9.11 内存与分配效率

内存优化应基于对正在减少的资源的清晰理解。

**区分分配与使用：** 减少分配次数不等于减少峰值内存。复用大缓冲可能减少分配开销却增加保留内存。测量相关量，而不是假定一个指标代表所有内存成本。

**临时存储：** 临时缓冲应有清晰所有权与有界生命周期。避免在有用生命周期之后保留大中间产物。引入缓冲复用时，测试先前请求或操作内容不能影响后续结果。

**避免过早池化：** 对象或缓冲池引入复杂度、容量决策与可能争用。仅当测量显示分配或初始化成本显著且更简单方法不足时才引入池化。

**资源限制：** 内存优化不得绕过已记录大小限制或把分配失败转换为伪造成功。资源耗尽必须遵循本文《错误处理与失败语义》章节。

### 9.12 缓存与记忆化

当昂贵操作用相同有效输入重复时，缓存可能有用。缓存必须定义：键语义；有效性条件；生命周期；容量或驱逐策略；内存成本；并发行为；失败行为；失效要求。

**正确性优先：** 缓存不得为在操作实际语义下不等价的输入返回结果。若结果依赖配置、dtype、布局、模型版本或其他上下文，缓存键或失效策略必须考虑该依赖。

**隔离：** 缓存不得允许请求特定可变状态在用户或操作之间泄漏。

**证据：** 缓存有效性应使用现实命中与未命中模式测量。改进合成重复输入基准的缓存可能无助于真实工作负载。必须考虑内存开销、未命中成本与失效复杂度。

### 9.13 基准设计与实现

基准应与普通正确性测试分离。

**计时区域：** 计时区域必须恰好包含基准所描述的工作。当夹具构建、随机数据生成、模型加载或其他搭建成本不是目标指标的一部分时排除它们。当它们有意属于工作负载的一部分时包含它们。

**输入准备：** 当测量重复操作延迟且输入准备不是目标的一部分时，在计时区域之外准备可复用输入数据。若分配是基准的主题，分配必须保持在计时区域内。

**结果消费：** 基准必须确保预期计算实际执行，且编译器不能轻易消除被测工作。使用基准框架的适当结果消费机制。

**避免仅基准语义：** 基准必须调用被评估的实际实现。不要为基准创建单独的简化实现，然后把其结果当作生产路径的性能。

**基准框架：** 工作区可以使用既有的 Rust 基准框架或仓库特定 harness。框架必须有意识地选择并一致使用以支持可比结果。框架本身不保证有效测量。基准设计与环境控制仍然必要。

### 9.14 回归检测

对稳定、重要且环境支持有意义比较的工作负载，应引入性能回归检查。

**回归阈值：** 阈值应说明：历史变异；测量开销；工作负载重要性；误报成本；未检测回归的成本。不要仅因易于配置就选择阈值。

**环境差异：** 来自不同硬件或编译器配置的结果不得在没有适当归一化或限定的情况下被当作直接等价比较。

**有噪声的 CI：** 性能 CI 可能因共享机器、热行为、虚拟化环境与竞争工作负载而有噪声。疑似回归应触发受控条件下的确认，而不是自动声称实现更慢。

**保留历史证据：** 对关键基准，保留足够历史结果以识别趋势并将突变回归与正常变异区分。保留机制可以是 CI artifact、基准数据库或其他仓库认可系统。除非项目需求证明合理，不要引入复杂性能数据平台。

### 9.15 权衡与接受决策

优化必须对照其完整成本评估。评审者应问：变更是否解决已证实瓶颈？测量改进是否可复现？是否改进预期工作负载？是否增加内存消耗？是否影响其他重要工作负载？是否添加新依赖？是否使错误处理复杂化？是否使数值行为更不稳定？是否需要更复杂 API？是否违反预期 crate 边界？改进能否被维护与重新验证？

关键热路径中小的稳定改进可能值得。无关紧要路径中同样小的改进可能不足以证明复杂度大幅增加。决策必须同时考虑测量价值与维护成本。

### 9.16 性能报告

每个重要性能变更应包含简明报告。报告必须区分实现状态、正确性验证、基准执行与测量支持的结论。

推荐模板：

- **目标：** 描述工作负载与预期改进。
- **基线：** 描述先前实现、基准配置与测量结果。
- **变更：** 描述实际实现变更与其检验的假设。
- **正确性：** 列出执行的相关测试及其结果。
- **测量：** 包含候选结果、单位、相关变异、环境与比较方法。
- **权衡：** 描述内存、初始化、复杂度、数值行为与其他工作负载的相关变化。
- **结论：** 选择适当的基于证据的状态：已实现——变更存在；正确性已验证——所需正确性检查通过；已基准测试——定义的基准已执行；已改进——可比测量支持改进；已回归——可比测量支持变慢；无结论——证据不足以确定结果。这些状态不可互换。变更可以是已实现、正确性已验证且已基准测试，而其性能结果仍无结论。

### 9.17 AI 辅助性能工程

AI 编码代理必须遵循与人类工程师相同的证据要求。AI 代理不得：发明基准测量；基于源码外观声称加速；把行数减少当作性能改进；没有证据声称向量化；假定分配减少意味着更低延迟；仅为改进基准结果而移除正确性检查；在基线与候选之间改变工作负载而不披露差异；没有可测试假设就引入投机复杂度；未运行时报告基准为已执行；仅基于微基准声称端到端改进。

若仓库访问、基准执行或合适硬件不可用，代理必须说明该限制。没有测量的优化提案可以作为假设提交。它不得被呈现为已验证性能改进。

### 9.18 已记录的 CPU 内核基线

**日期：** 2026-10-10。**环境：** macOS 27.0.1、aarch64-apple-darwin（18 核）、rustc 1.99.0、edition 2024，`cargo bench --bench kernels`（criterion，`--warm-up-time 0.5 --measurement-time 2`）。

| 内核 | 基线中位延迟 |
| --- | --- |
| binary/matmul256 | 974.6 µs |
| attention/seq128heads8dim64（causal） | 1.2332 ms |
| softmax/rows512cols4096 | 2.5192 ms |
| rmsnorm/rows512cols4096 | 1.1817 ms |
| elementwise/silu（1M） | 1.0724 ms |
| elementwise/gelutanh（1M） | 1.5492 ms |
| rope/seq128heads8dim64 | 85.54 µs |
| embedding/gather128 | 6.69 µs |
| binary/add（256²） | 4.76 µs |

**已实施的优化：** `cpuattention` 在因果模式下只为查询位置 `s` 计算键 `0..=s`，跳过其无法注意到的键位置，使这些位置不再被评分、指数化或归一化。非因果调用的最坏复杂度不变。

**测量方法：** 交错 A/B（同一会话内交替测量优化版与 `git` 原始版，各 3 轮），因为单次「相对已存基线」的比较被证明受到系统负载漂移污染——未修改的 `rope` 与 `rmsnorm` 也显示出 −4% 至 −8% 的变化，说明该比较不可用。交错测量得到：

| 轮次 | 优化版中位 (ms) | 原始版中位 (ms) | 提升 |
| --- | --- | --- | --- |
| 1 | 1.1103 | 1.2446 | 10.8% |
| 2 | 1.1060 | 1.2179 | 9.2% |
| 3 | 1.1066 | 1.2146 | 8.9% |

优化版分布紧（1.1060–1.1103 ms），原始版分群明确（1.2146–1.2446 ms），约 9% 的提升超出噪声带。正确性由 `cargo test --workspace`（735 通过 / 0 失败）与 `bash scripts/check.sh`（exit 0）验证。仅 `cpuattention` 被修改；其他内核的延迟不声称变化。

**来源说明：** 初版假设认为因果注意力「浪费了约一半点积算力」。该假设被证伪——原实现的分支已跳过被遮蔽位置的点积；实际收益来自去除逐位置分支与循环迭代，并让指数化与归一化仅遍历有效区间。

## 10. 评审清单

本文档只有一个统一评审清单，适用于错误处理、公开 API、性能与测试变更。以下每个相关生产变更都应逐项核对。

### 10.1 语义与错误契约

- [ ] 错误是否表示真实且可区分的失败？
- [ ] 预期缺失是否被适当表示？
- [ ] 无效输入与内部不变量破坏是否被区分？
- [ ] 资源耗尽、取消与超时是否按契约处理？
- [ ] 部分成功在适用时是否被显式表示？
- [ ] 运行期失败是否不通过 `panic!`、`unwrap()` 或 `expect()` 传播？
- [ ] 是否防止错误变成伪造默认值或静默成功？
- [ ] 重试是否有界且安全？
- [ ] 失败后资源与持久状态是否处于已记录状态？
- [ ] 取消是否被尊重？

### 10.2 架构、所有权与依赖

- [ ] 错误类型是否属于正确的 crate？
- [ ] 变更是否保持允许的依赖方向？
- [ ] 错误转换是否在有意义的抽象边界执行？
- [ ] 公开 API 是否避免泄漏不必要的实现细节？
- [ ] 是否引入被禁止的依赖方向或循环依赖？
- [ ] 是否引入 unsafe 代码？
- [ ] 共享模型权重是否不含请求级可变状态？
- [ ] 依赖与特性组合边界是否被检查？

### 10.3 公开 API：范围、可见性与设计

- [ ] 该公开接口是否有具体消费者？
- [ ] 所选可见性层级是否是最窄的实用层级？
- [ ] re-export 是否有意？
- [ ] 实现细节是否保持私有？
- [ ] 接口的稳定性类别是否清晰？
- [ ] API 是否表示一个连贯能力？
- [ ] 抽象是否由真实需求证明合理？
- [ ] 函数签名与所有权语义是否清晰？
- [ ] 类型参数、trait bound 与生命周期是否必要？
- [ ] 静态分发是否足够，或动态分发是否有理由？
- [ ] 是否避免了隐藏全局行为与不必要状态？

### 10.4 正确性、数值与并发

- [ ] 前置条件与后置条件是否已记录？
- [ ] 错误是否显式且可操作？
- [ ] 数值与变更语义是否清晰？
- [ ] 并发保证是否准确？
- [ ] 边界情形是否覆盖？
- [ ] 所需正确性测试是否通过？
- [ ] 边界行为是否保持？
- [ ] 相关处数值行为是否验证？
- [ ] 错误处理是否保持正确？

### 10.5 运行期行为、诊断与安全

- [ ] 是否保留足够的源上下文？
- [ ] 敏感值是否被排除在外部信息与不当日志之外？
- [ ] 错误是否在适当层记录？
- [ ] 机器可读决策是否基于带类型变体或稳定码而非信息字符串？
- [ ] 清理与部分失败行为在相关时是否测试？
- [ ] 边界条件与溢出路径在适用时是否测试？

### 10.6 性能：目标、测量与维护

- [ ] 目标工作负载是否明确？
- [ ] 主要指标是否适当？
- [ ] 是否已有基线，或已记录其缺失？
- [ ] 疑似瓶颈是否有证据支撑？
- [ ] 优化假设是否可测试？
- [ ] 基准输入与配置是否记录？
- [ ] 基线与候选工作负载是否可比？
- [ ] 相关环境差异是否记录？
- [ ] 测量变异是否被考虑？
- [ ] 单位与计算方法是否清晰？
- [ ] 复杂度是否由证据证明合理？
- [ ] 内存与初始化权衡是否被理解？
- [ ] 回归覆盖是否适当？
- [ ] 最终性能声明是否与证据一致？
- [ ] 是否未引入被禁止的依赖方向与 unsafe？

### 10.7 验证与证据

- [ ] 相关错误路径是否被测试覆盖？
- [ ] 相关测试是否通过？
- [ ] 文档示例在可行时是否准确且被测试？
- [ ] 相关特性配置是否被检查？
- [ ] 所需算子基准是否存在？
- [ ] 最终差异是否被评审？
- [ ] 未验证的检查与剩余风险是否被诚实报告？
- [ ] 下游消费者与实现是否被考虑？
- [ ] trait bound、字段、枚举变体与特性要求的变更是否被评审？
- [ ] 是否需要弃用或迁移指引？
- [ ] 任何稳定性承诺是否有实际项目策略支撑？

## 11. 完成定义

一个任务只有在其适用要求全部满足时才完成。以下是本文档唯一的统一完成定义。

### 11.1 通用完成条件

- [ ] 目标与验收标准已满足。
- [ ] 变更保持在已批准范围内。
- [ ] 既有架构边界仍然有效。
- [ ] 相关错误与失败模式被显式处理。
- [ ] 适用测试实际运行并通过。
- [ ] 已执行所需的专项验证。
- [ ] 公开契约与文档一致。
- [ ] 最终差异不含无法解释的变更。
- [ ] 性能声明由证据支撑。
- [ ] 剩余局限已披露。
- [ ] 验收标准显式；相关单元或契约测试存在；相关失败路径已覆盖。
- [ ] 现有测试在已验证范围内继续通过。
- [ ] 公开行为与文档一致；无无关变更。
- [ ] 测试结果与局限被准确报告。

### 11.2 Bug 修复

- [ ] 缺陷在可行时已有可复现测试。
- [ ] 测试验证原始失败模式。
- [ ] 修正不引入无关变通。
- [ ] 相关回归测试通过。

### 11.3 新算子

- [ ] 边界测试存在。
- [ ] 数值正确性测试存在。
- [ ] 至少一个基准存在。
- [ ] 支持的 dtype 与布局行为在适用时已记录并测试。
- [ ] 相关处错误行为已测试。
- [ ] 适用时梯度行为已测试。
- [ ] 性能声明与测量证据一致。

### 11.4 架构变更

- [ ] 依赖方向已检查。
- [ ] 未引入被禁止的依赖环。
- [ ] 公开契约与受影响集成测试已评审。
- [ ] 文档反映预期架构。
- [ ] 变更保持可独立测试。

### 11.5 公开 API 变更

- [ ] 消费者与架构归属已被理解。
- [ ] 接口暴露的功能不超过必需。
- [ ] 所有权、错误、变更与行为契约显式。
- [ ] 相关数值与并发保证已记录。
- [ ] 接口有适当文档与测试。
- [ ] 兼容性影响已评审。
- [ ] 相关验证已运行且结果被准确报告。
- [ ] 未引入循环依赖或被禁止的 unsafe 代码。
- [ ] 最终差异不含意外可见性扩张。
- [ ] 任何未解决的局限已记录。

### 11.6 性能变更

- [ ] 正确性已建立。
- [ ] 基线适当且可比。
- [ ] 基准方法与环境已记录。
- [ ] 变异与测量局限已被考虑。
- [ ] 报告的结论与证据一致。

此外：

- 被阻塞的任务不是已完成的任务。
- 部分实现的功能必须被描述为部分。
- 未测量的优化不得被描述为已证实的改进。
- 通过的构建不得被呈现为完整正确性的证明。
- 公开 API 变更不因代码能编译就算完成。

## 12. 一致性与采纳

本文档定义各领域的目标标准，不声明工作区现有实现、基准或测试已符合。

### 12.1 逐 crate 审计

每个 crate 应独立审计。对每个发现，记录：crate 与受影响操作；当前行为（含当前失败行为）；所需行为；风险与影响；最小补救；所需测试；验证状态。

对于性能与测试，还记录：主要契约或主要工作负载；主要指标；现有测试或基准覆盖；基线可用性；已知未测试的失败模式或瓶颈；所需边界与数值测试；集成要求；架构检查要求；内存与并发约束；回归检测策略；验证状态。

各领域可按需增量采纳，每次变更形成一个小的、可独立测试的阶段。

### 12.2 一致性状态

使用以下状态：

- **拟定（Proposed）：** 所需行为或要求已指定但未验证。
- **已验证（Verified）：** 实现与相关测试/基准证明符合。
- **不符合（Non-conforming）：** 存在已知违规或覆盖缺口。
- **阻塞（Blocked）：** 验证或补救依赖未解决的依赖、设计决策或环境能力。

### 12.3 结论记录纪律

- 不得仅基于成功的工作区编译就把 crate 标记为已验证。编译不证明正确的失败语义。
- 通过的测试命令不得被解释为所有契约、错误路径、支持平台与数值边界都已被验证的证据。
- crate 不得仅因能编译、通过单元测试或包含基准源码就被标记为性能已验证。
- 从未执行过的基准不是测量证据。
- 改变命名标准、拒绝列表或门的变更，必须用已执行的命令及其退出码更新 conformance 记录中的对应行。

## 13. 结语

工作流的目的不是最大化流程开销，而是最小化误解、隐藏耦合、回归与无依据声明的成本。对每个变更，优先选择满足契约且能被独立验证的最小实现。没有具体需求不要增加复杂度；不要为便利而削弱安全或正确性；不要把活动与进展混为一谈。只有当预期结果由证据确立、边界保持完整、剩余局限明确时，任务才算完成。

错误处理的目的不是让失败消失，而是让失败显式、有意义、有界、可观测且可安全响应。绝不把未知失败变成虚假成功。绝不用错误抽象掩盖架构缺陷。绝不在没有证据时声称恢复。存疑时：1. 保留失败。2. 保留其含义。3. 只添加有用上下文。4. 把它传播到拥有恢复决策的层。5. 测试失败路径。6. 准确报告已与未验证的内容。

命名是一份契约。读者必须能从动词与名词推断语义而无须阅读实现。保持动词集封闭、同义词集禁用，使机械门保持锐利、低噪声。

公开 API 是契约，不是便利机制。只暴露真实消费者需要的部分。优先显式类型、连贯 trait、可预测所有权与有意义的错误。保持内部实现细节可替换。有意识地演进接口，并用证据支撑每个兼容性或性能声明。长期目标不是最大化可复用抽象的数量，而是让最小的一组接口足以使系统在实现演进中保持正确、可组合、可维护且可适应。

测试套件存在的目的是检测错误行为、保留契约并使工程声明可验证。测试契约。测试边界。测试失败路径。单独测量性能。只报告证据支持的内容。目标不是最大化测试数量，而是从可维护的验证系统中获得最大量的有意义、独立的信心。

性能工程是假设、测量、验证与有纪律权衡的过程。测量瓶颈。保持正确性。做最小必要变更。比较等价工作负载。只报告证据支持的内容。目标不是产出最复杂的实现或最令人印象深刻的基准数字，而是构建一个性能特征被理解、可复现、可维护且适合其预期工作负载的系统。
