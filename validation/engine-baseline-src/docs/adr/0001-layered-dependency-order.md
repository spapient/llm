# 0001：用显式的层表代替"约定俗成的分层"

- 状态：已采纳（2026-11-12 修订：数值注册表已删除，见「修订」）
- 日期：2026-11-12

## 背景

仓库曾经只有 `cutile` 与三个数据 crate 有真实依赖边，其余 16 个成员是零依赖的裸壳，
"五层架构"只写在文档里。文档里的约束有两个失败模式：

1. **加成员时没人读**：`members = ["crates/*"]` 让 `cargo new` 出来的目录自动成为"架构成员"，
   于是 `crates/` 变成目录列表而不是架构；
2. **写下来也无法判定**：`crates/` 里到底该不该有 `config`、`data` 与 `engine` 谁在上面，
   靠形容词无法评审，只能靠争论。

## 决策

把每个成员归入 `docs/ARCHITECTURE.md` 第一节的七层之一，并只保留一条规则：

> 依赖只能指向更低的层；同层内只能依赖层表中更靠左的成员，不允许反向。

- `layer`（1–7）表达职责分层；
- 同层先后由层表里的成员顺序表达，顺序有争议就在评审里说明理由；
- 层与表内顺序构成偏序，严格递减天然无环，不需要额外的环检测。

## 为什么不是别的做法

- **不引入 `cargo-deny` / `cargo-machete` 作为唯一手段**：它们检查许可证与未使用依赖，
  不检查"这个依赖方向是否符合本项目的分层"。
- **不用目录名推断层级**（`crates/runtime/*`）：那只是把隐式约定换个写法，仍然无法判定
  同层先后，而且移动目录会破坏历史。
- **不做环检测**：严格递减的偏序天然无环，多写一个环检测等于多一条可以写错的代码。

## 后果

- 新增成员要在层表里加一行，"顺手新建目录"不再能变成架构成员；
- 层表是显式列表，新增/迁移成员会产生一次可评审的 diff；
- 排序一旦需要调整（例如 `nn` 要下移），必须连着所有受影响成员的边一起改——这正是期望：
  层级变动本就应该是一次显式的架构决策。

## 修订

- 2026-11-12：`llm-xtask` 及其 `check-graph` 已删除（见 CHANGELOG）。分层与依赖规则不变，
  “注册表 ↔ `Cargo.toml`”的一致性一度改为评审时人工核对；P0-3 起由 `tests/architecture.rs`
  在 `cargo test` 里重新自动执行（成员集合、边集与方向、所有权表）。
- 2026-11-12：`docs/architecture/layers.toml` 一并删除。最初的实现给每个成员分配
  `(layer, rank)` 数值并断言 `rank / 100 == layer`，目的是让脚本判定同层先后；脚本删除后
  这份数值失去消费方，只留下“改一处必须同步两处”的负担。现在层表是唯一事实源，同层先后
  由表内顺序表达，不再有数字。
