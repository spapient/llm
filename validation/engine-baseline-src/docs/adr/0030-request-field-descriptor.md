# 0030：请求文法改为编译期字段描述符（不引入解析器）

- 状态：已采纳（P0 落地）
- 日期：2026-11-17
- 相关：[0022](0022-build-time-corpora.md)（运行期不带解析器）；设计取证见 [`../serve-deep-optimization-design.md`](../serve-deep-optimization-design.md) D2/C1

## 背景

`Request` 原有三个字段（`id: u64`、`prompt: String`、`max_new: usize`），每个字段各有一套
setter；字段名、解析类型、错误文案三处重复。ADR 0022 之后运行期不允许引入 TOML/JSON 解析器，
方案不能是 serde 之类的声明式反序列化。

## 决策

用编译期字段闭集表驱动一行解析：

- `Field` 私有枚举列出全部字段；`ALL` 是字段清单的唯一事实源，`key()` 派生线上键名，
  `from_key()` 按键名找回字段，`known_names()` 派生"只认哪些键"的错误清单；
- 累积器按字段槽位走泛型解析入口：文本槽位走 `set_text`，数值槽位走泛型 `set_parsed<T: FromStr>`；
- 重复键、未知键、缺字段、解析失败的判定共用同一条路径，错误文案逐字保留。

新增字段 = `Field` 加一条变体并补槽位；键名清单与未知键文案随之派生，不再手抄匹配臂与消息。

## 备选方案

- proc-macro `#[request(id: u64, prompt: String, max_new: usize)]` 生成解析器：暂缓 P2。
  文法只有三个字段，宏收益抵不上注解层扩展成本；等字段数稳定增长后再评估。
- 保持手写 setter：第四个字段（如 `temperature`）到来时重复翻倍。

## 后果

### 正面

- 键名、类型、缺省文案单一来源；新增字段的改动面收敛到枚举与槽位两处。
- 不引入运行期解析依赖，符合 ADR 0022。

### 负面

- const 上下文里解析错误要预先映射；泛型 `T: FromStr` 的错误信息沿既有 `invalid` 文案给出。

### 取舍

表驱动优先于宏；文法字段稳定且少时，编译期表比过程宏更透明。

## 不做

- 不为三个字段上提 proc-macro；不支持嵌套结构或数组值。

## 修订

- 2026-11-17：初稿并落地；`Field` 私有，`Request` 公开契约与错误文案不变。
