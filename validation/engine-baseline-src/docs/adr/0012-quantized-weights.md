# 0012：量化权重的分组与宽度必须同源

- 状态：已采纳
- 日期：2026-11-12

## 背景

[ADR 0009](0009-real-weights-to-model-floor.md) 把"权重条目 → 层栈 → 模型下界"接通之后，
剩下的一处不诚实是：**真实量化模型每一个都读不出来**。

真实的 4 位量化 checkout 里，一个投影张量从不成对出现：

```
blk.0.attn_q.weight   dtype U8    shape [out, in/2]     ← 4 位打包，一字节两个 nibble
blk.0.attn_q.scales   dtype F16   shape [out, groups]   ← 每个分组一个缩放因子，group = in / groups
```

于是有四处同时坏掉（第四处最危险，因为它不报错）：

1. `Stack::from_header` 把 `blk.0.attn_q.scales` 也当成一层投影（秩 2），模型层数翻倍；
2. `blk.0.attn_q.weight` 的元素类型是 `U8`（映射到 `I8`），`WeightFormat::of_dtype` 说"i8 没有这个
   格式的投影算子"，于是**真正能算的那一层无法计价**；
3. `gemv_i4` 声明的分组是 32 个元素一组，而文件里的分组（由标度形状决定）可能是 128——这是
   "分组不同不能共用同一条内核"，必须被拒绝，而不能按默认值 32 顶上去。

4. **8 位元素类型的第二维是字节数，不是元素数**。若把 `shape[1]` 当输入宽度，`[64, 64]` 的打包
   权重会被读成"64 个输入"，流量与运算次数都少一半——不会报错，只会给出一个错得很像对的数。

## 决策

### 1. 推断集中在 `weights::quant`，只有一处

`Header::quantization(name) -> Result<Option<Quantized>>`：

- 名字规则按"越具体越先"匹配四种命名族：`{name}_scale`、`{name}_scales`、`{base}.scales`、
  `{base}.scale`（`base` = 去掉末尾 `.weight`）。不在其中的命名不会被误认。
- `Quantized` **同时**给出 `group()`、`in_features()`、`out_features()`、`scales()`。宽度与分组来自
  同一次推断，所以不可能出现"分组按 128 算、宽度按 64 算"的错配。
- 三条硬约束：两者秩都必须是 2；输出维必须相等；标度第二维必须整除输入维（`group` 要是整数）。
- "它到底是不是 4 位打包"用**字节数事实**判定：`out × ceil(in / 2)` 必须等于条目长度。

### 2. 三种结局的分界是"能不能解释成另一种合法方案"

| 情形 | 返回 | 理由 |
|---|---|---|
| 没有标度伙伴 | `Ok(None)` | 不是量化，按元素类型处理 |
| 形状自相矛盾（秩不对、输出维不等、不整除、`groups == 0`） | `Err(Invalid)` | 文件说它是量化却对不上，猜下去每个数都错 |
| 打包口径不符、或标度不是浮点 | `Ok(None)` | 那是**另一种**方案（int8 逐元素、整数标度），不猜 |

"不猜"不是偷懒：`Ok(None)` 会让上层按元素类型给出诚实的无法计价理由，而编一个分组只会得到一个
看起来有数、其实错的下界。

### 3. `nn` 侧只有两处改动

- `Stack::from_header` 用 `header.scales_names()` 把标度条目排除出层清单——排除用的判断与推断分组
  用同一个 `quantization`，因此没有第二份命名规则。
- `projection` 遇到量化条目**先问标度**，宽度与分组一起取；否则才按 `shape` 与 `dtype` 判断。

`WeightFormat::int4(group)` 与内核声明的分组比对不上时，`Linear::bounds` 给出点名诊断：

```
层 `blk.0.attn_q` 的权重按 128 个元素一组量化，而内核声明的是 32 个元素一组：
分组不同不能共用同一条内核，无法推出下界
```

## 后果

- 一个真实形态的量化文件（`U8 [64, 64]` + `F16 [64, 4]`）现在得到 **1 层**、可计价、未覆盖清单为空；
  同一层权重的解包视图（`U4 [64, 128]`）推出**逐位相同**的下界，这条由测试
  `a_quantized_entry_and_its_unpacked_view_declare_the_same_floor` 钉住。
- group 128 的模型（`scales [64, 1]`）不再被静默按 32 计价，而是如实报"分组不同"。
- 逐元素 int8 与"打包 nibble"在形状上无法区分，本层如实把宽度读成两倍；上层拿算子声明的分组一比
  就会被拒绝，而不是算出一个用错分组的流量。
- 代价：`Header::scales_names()` 是 `O(n²)` 次名字查找。条目数量级是几千，成本可忽略；换来的是
  "命名规则只有一份"。

## 未决

- **只有 4 位打包**：2 位 / 3 位打包的字节数口径不同，需要各自的可测量事实，不能靠"除以 2"外推。
- **零点是第四种元素**：不少格式（AWQ / GPTQ 的某些变体）还带 `zero_points`（int8，与标度同形状）。
  它不改变分组，但改变反量化公式；等到内核侧真的支持非对称量化时再进 `Quantized`，现在加了只会
  是一个没人读的字段。
- **分组不整除输入时**目前报 `Invalid`。若真实导出确实用 pad 到整组的写法，需要先看到一个这样的
  文件，再决定是接受 pad 还是要求导出方修正。
